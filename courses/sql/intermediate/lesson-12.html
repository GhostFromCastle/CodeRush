Индексы и EXPLAIN

~30 минут Средний уровень Теория и Практика

Запрос, который на сотне строк выполняется мгновенно, на миллионе может занять минуты. Причина обычно одна: база перебирает всю таблицу. Индексы решают эту проблему - но не всегда и не бесплатно.

В этом уроке мы:

  • Поймём, что такое индекс и как он устроен.
  • Научимся создавать индексы под конкретные запросы.
  • Разберём случаи, когда индекс не помогает.
  • Научимся читать план выполнения через EXPLAIN.

Аналогия

Представьте книгу на тысячу страниц без оглавления. Найти упоминание «Байкал» можно только перелистывая всё подряд. Оглавление и алфавитный указатель - это индекс: отдельная структура, которая позволяет прыгнуть сразу в нужное место.

В базе индекс - это отсортированная структура (обычно B-дерево), где хранятся значения столбца и ссылки на строки.

Создание индекса

CREATE INDEX idx_orders_customerON orders (customer_id);

После этого запрос

SELECT * FROM orders WHERE customer_id = 1;

не будет перебирать таблицу: база найдёт нужные строки через индекс.

Уникальный индекс заодно запрещает дубли:

CREATE UNIQUE INDEX idx_users_email ON users (email);

Он делает то же, что ограничение UNIQUE, но может быть создан на существующей таблице.

Составные индексы

Индекс может включать несколько столбцов:

CREATE INDEX idx_orders_customer_dateON orders (customer_id, created_at);

Он поможет запросам, где фильтр начинается с customer_id:

WHERE customer_id = 1                                  -- работаетWHERE customer_id = 1 AND created_at > '2026-01-01'    -- работаетWHERE created_at > '2026-01-01'                        -- НЕ работает

Правило «левого префикса»: индекс используется, если условие накрывает его начало. Порядок столбцов в индексе поэтому важен - первым ставят самый избирательный и самый частый в фильтрах.

Когда индекс не помогает

  • Функция над столбцом. WHERE LOWER(email) = 'a@b.c' не использует обычный индекс по email. Нужен функциональный индекс или хранение нормализованного значения.
  • Поиск по подстроке. LIKE '%анна%' не может использовать B-дерево: неизвестно, с чего начинать. LIKE 'Анна%' - может.
  • Низкая избирательность. Индекс по столбцу «пол» бесполезен: он вернёт половину таблицы, и база всё равно пойдёт читать строки.
  • Маленькая таблица. На сотне строк дешевле прочитать всё целиком.
  • Несовпадение типов. WHERE id = '5' может помешать использованию индекса в строгих СУБД.

Цена индекса

Индекс ускоряет чтение, но замедляет запись: при каждом INSERT, UPDATE и DELETE его нужно обновить. Он занимает место на диске.

Поэтому не стоит индексировать всё подряд. Практическое правило: индексы нужны на столбцах, по которым часто фильтруют и соединяют таблицы, а также на внешних ключах.

Внешние ключи индексируются не везде

PostgreSQL и MySQL автоматически создают индекс для внешнего ключа, SQLite - нет. Если в SQLite часто ищут заказы по customer_id, индекс стоит создать вручную.

EXPLAIN

Самый надёжный способ узнать, использует ли база индекс, - посмотреть план запроса:

EXPLAIN QUERY PLANSELECT * FROM orders WHERE customer_id = 1;

В SQLite вывод будет примерно таким:

SEARCH orders USING INDEX idx_orders_customer (customer_id=?)

Слово SEARCH с индексом - хороший знак. SCAN orders означает полный перебор.

В PostgreSQL:

EXPLAIN ANALYZESELECT * FROM orders WHERE customer_id = 1;

ANALYZE выполняет запрос и показывает реальное время и количество строк. Ищите в плане Seq Scan (перебор) там, где ожидали индекс.

Как подбирать индекс

  1. Найдите медленный запрос (лог медленных запросов или EXPLAIN).
  2. Посмотрите, по каким столбцам идёт фильтр и соединение.
  3. Создайте индекс начиная с самого избирательного столбца.
  4. Повторите EXPLAIN и сравните.
  5. Проверьте, не ухудшилась ли запись.

Не создавайте индексы «на всякий случай»: каждый из них нужно обслуживать.

Шпаргалка

  • CREATE INDEX создать индекс
  • UNIQUE INDEX индекс без дублей
  • составной индекс порядок столбцов важен
  • EXPLAIN план запроса
  • SCAN полный перебор
  • SEARCH поиск по индексу

Если что-то не работает

  • Индекс создан, но запрос медленный. Проверьте EXPLAIN: возможно, условие не покрывает левый префикс индекса.
  • «Index already exists». Дайте другое имя или используйте IF NOT EXISTS (не во всех СУБД).
  • Запись стала медленнее. Слишком много индексов. Удалите неиспользуемые: DROP INDEX idx_name;
  • LIKE не ускоряется. Поиск по подстроке требует полнотекстового индекса (FTS в SQLite, GIN в PostgreSQL).
  • «Индекс есть, а запрос всё равно медленный». В условии функция над столбцом (LOWER(email)) или поиск с % в начале - индекс не применяется. Смотрите EXPLAIN, а не догадывайтесь.

Практика

Задача 1. Индекс для заказов

Создайте индекс, который ускорит поиск заказов конкретного клиента за период. Проверьте план запроса до и после.

Подсказка

Составной индекс: (customer_id, created_at). Порядок именно такой: сначала клиент, потом дата.

Решение учителя 
CREATE INDEX idx_orders_customer_dateON orders (customer_id, created_at);EXPLAIN QUERY PLANSELECT * FROM ordersWHERE customer_id = 1  AND created_at >= '2026-01-01';
Задача 2. Найдите бесполезный индекс

Есть индекс CREATE INDEX idx_name ON users(name). Какие из запросов его используют, а какие нет?

A: WHERE name = 'Анна'B: WHERE LOWER(name) = 'анна'C: WHERE name LIKE 'Ан%'D: WHERE name LIKE '%нна'
Подсказка

Индекс работает, когда сравнивается сам столбец или его начало. Функция и поиск с % в начале мешают.

Решение учителя

A и C используют индекс. B - нет, потому что функция над столбцом. D - нет, поиск по подстроке требует полного перебора или отдельного полнотекстового индекса.

Задача 3. Замер

Сгенерируйте таблицу на 100 000 строк, замерьте время запроса без индекса и с ним. Используйте EXPLAIN и секундомер клиента.

Подсказка

В SQLite можно вставить данные из рекурсивного CTE (разберём позже) или сгенерировать CSV. Главное - сравнить SCAN и SEARCH в плане.

Решение учителя 
-- до индексаEXPLAIN QUERY PLAN SELECT * FROM big WHERE code = 777;-- SCAN bigCREATE INDEX idx_big_code ON big (code);-- послеEXPLAIN QUERY PLAN SELECT * FROM big WHERE code = 777;-- SEARCH big USING INDEX idx_big_code (code=?)

На 100 000 строк разница обычно заметна уже в миллисекундах, а на миллионах строк - в десятки раз.

Задача 4. Индекс по статусу и дате

Создайте индекс, который ускорит отчёт «оплаченные заказы за период». Проверьте план запроса.

Подсказка

Составной индекс: сначала статус, затем дата.

Решение учителя 
CREATE INDEX idx_orders_status_date ON orders (status, created_at);EXPLAIN QUERY PLANSELECT * FROM ordersWHERE status = 'paid'  AND created_at >= '2026-01-01';
