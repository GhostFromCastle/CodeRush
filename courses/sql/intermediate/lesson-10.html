CREATE, ALTER и нормализация

~35 минут Средний уровень Теория и Практика

До сих пор мы работали с готовыми таблицами. Пора научиться проектировать свои. Это навык, который отличает разработчика, умеющего писать запросы, от того, кто умеет строить приложение, которое не развалится через полгода.

В этом уроке мы:

  • Разберём CREATE TABLE, ALTER TABLE и DROP TABLE.
  • Поймём, зачем нужны три нормальные формы.
  • Превратим плохую таблицу в хорошую схему.
  • Узнаем, когда денормализация оправдана.
Аналогия

Кладовка: если одну вещь кладут в пять коробок, порядок теряется. Нормализация - это подписанные полки.

CREATE TABLE

CREATE TABLE categories (    id    INTEGER PRIMARY KEY,    title TEXT NOT NULL UNIQUE);CREATE TABLE products (    id          INTEGER PRIMARY KEY,    category_id INTEGER NOT NULL,    title       TEXT NOT NULL,    price       INTEGER NOT NULL CHECK (price >= 0),    FOREIGN KEY (category_id) REFERENCES categories (id));

Порядок важен: нельзя сослаться на таблицу, которой ещё нет. Сначала создаём справочник категорий, потом товары.

ALTER TABLE

Схема меняется со временем. Основные операции:

ALTER TABLE products ADD COLUMN description TEXT;ALTER TABLE products RENAME COLUMN title TO name;ALTER TABLE products ADD COLUMN stock INTEGER NOT NULL DEFAULT 0;

Удаление столбца поддерживается в SQLite с версии 3.35, в MySQL и PostgreSQL - ALTER TABLE products DROP COLUMN description;.

Добавить обязательный столбец в непустую таблицу можно только с DEFAULT: иначе у существующих строк не будет значения.

DROP TABLE

DROP TABLE IF EXISTS temp_data;

IF EXISTS спасает от ошибки, если таблицы нет. Удаление таблицы необратимо: данные исчезают вместе со структурой.

Плохая схема

Представьте таблицу заказов, которую «слепили» в Excel и перенесли в базу:

order_idcustomerphoneproductstotal
1Анна+79990000001Ноутбук, Мышь76500
2Борис+79990000002Монитор30000
3Анна+79990000001Кабель400

Проблемы:

  • Телефон Анны дублируется. Изменится - придётся править несколько строк.
  • В одной ячейке список товаров. Нельзя посчитать, сколько продано мышей.
  • Итого хранится отдельно и может разойтись с реальной суммой позиций.

Первая нормальная форма (1NF)

В каждой ячейке - одно неделимое значение. Списки в столбце запрещены: для них нужна отдельная таблица.

-- было: products = 'Ноутбук, Мышь'-- стало: отдельные строки в order_items

Вторая нормальная форма (2NF)

Каждый неключевой столбец зависит от всего ключа, а не от его части. Проблема появляется в таблицах с составным ключом.

Если ключ (order_id, product_id), а в строке лежит название товара, то название зависит только от product_id. Значит, его место - в таблице products.

Третья нормальная форма (3NF)

Нет транзитивных зависимостей: неключевой столбец не должен зависеть от другого неключевого.

В заказе хранится customer_id и customer_phone. Телефон зависит от клиента, а не от заказа - это нарушение. Телефон должен жить в customers.

Хорошая схема

CREATE TABLE customers (    id    INTEGER PRIMARY KEY,    name  TEXT NOT NULL,    phone TEXT UNIQUE);CREATE TABLE orders (    id          INTEGER PRIMARY KEY,    customer_id INTEGER NOT NULL,    created_at  TEXT NOT NULL DEFAULT CURRENT_DATE,    FOREIGN KEY (customer_id) REFERENCES customers (id));CREATE TABLE order_items (    order_id   INTEGER NOT NULL,    product_id INTEGER NOT NULL,    quantity   INTEGER NOT NULL CHECK (quantity > 0),    price      INTEGER NOT NULL CHECK (price >= 0),    PRIMARY KEY (order_id, product_id),    FOREIGN KEY (order_id) REFERENCES orders (id) ON DELETE CASCADE,    FOREIGN KEY (product_id) REFERENCES products (id));

Обратите внимание на price в order_items: он дублирует цену товара намеренно. Цена в каталоге может измениться, а в заказе должна остаться той, по которой покупали. Это не ошибка, а фиксация факта.

Нормализация - не религия

Иногда схему сознательно денормализуют: хранят итог заказа, чтобы не считать его каждый раз, или дублируют имя товара в отчёте. Это допустимо, если вы понимаете цену - данные нужно синхронизировать. Правило: сначала нормальная схема, потом осознанная денормализация под конкретную нагрузку.

Шпаргалка

  • CREATE TABLE создать таблицу
  • ALTER TABLE изменить схему
  • DROP TABLE удалить таблицу
  • 1NF атомарные значения
  • 2NF зависимость от всего ключа
  • 3NF без транзитивных зависимостей

Если что-то не работает

  • «Table already exists». Используйте CREATE TABLE IF NOT EXISTS или удалите старую.
  • «Cannot add a NOT NULL column with default value NULL». Добавляйте обязательный столбец с DEFAULT или сначала заполните данные.
  • Не удаётся удалить таблицу. На неё ссылаются внешние ключи. Сначала уберите зависимости.
  • После нормализации запросы стали сложнее. Это нормальная плата за отсутствие дублей. Сложность уходит в JOIN, который база выполняет эффективно.
  • «Переименовали группу - правили 200 строк». Признак плохой схемы: одно и то же значение хранится многократно. Нормализация убирает эту рутину.

Практика

Задача 1. Библиотека

Спроектируйте схему из трёх таблиц: authors, books, loans (выдачи книг). Продумайте ключи и связи.

Подсказка

У книги один автор - books.author_id. Выдача связывает книгу и читателя, поэтому нужна ещё таблица readers. В loans храните даты выдачи и возврата.

Решение учителя
SQL 
CREATE TABLE authors (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE books (
    id        INTEGER PRIMARY KEY,
    author_id INTEGER NOT NULL,
    title     TEXT NOT NULL,
    year      INTEGER,
    FOREIGN KEY (author_id) REFERENCES authors (id)
);

CREATE TABLE readers (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE loans (
    id         INTEGER PRIMARY KEY,
    book_id    INTEGER NOT NULL,
    reader_id  INTEGER NOT NULL,
    taken_at   TEXT NOT NULL DEFAULT CURRENT_DATE,
    returned_at TEXT,
    FOREIGN KEY (book_id) REFERENCES books (id),
    FOREIGN KEY (reader_id) REFERENCES readers (id)
);
Задача 2. Найдите нарушение

В таблице orders есть столбцы: id, customer_id, customer_email, product_list, total. Какие нормальные формы нарушены?

Подсказка

product_list - список в ячейке (1NF). customer_email зависит от клиента, а не от заказа (3NF).

Решение учителя

Нарушены 1NF (список товаров в одной ячейке) и 3NF (email клиента - зависимость от другого неключевого поля). Решение: таблицы order_items и customers, в заказе остаётся только customer_id. total можно оставить как кэш, но тогда его нужно пересчитывать при изменении позиций.

Задача 3. Измените схему

Добавьте в products столбец description и столбец is_active со значением по умолчанию 1. Затем переименуйте title в name.

Подсказка

Три команды ALTER TABLE. Для логического флага в SQLite используют INTEGER DEFAULT 1.

Решение учителя 
ALTER TABLE products ADD COLUMN description TEXT;ALTER TABLE products ADD COLUMN is_active INTEGER NOT NULL DEFAULT 1;ALTER TABLE products RENAME COLUMN title TO name;
Задача 4. Разделить группы

Есть таблица students(id, name, group_name). Вынесите группы в отдельную таблицу groups и свяжите их.

Подсказка

Создайте groups, заполните уникальными названиями, добавьте group_id и обновите значения.

Решение учителя 
CREATE TABLE groups (    id    INTEGER PRIMARY KEY,    title TEXT NOT NULL UNIQUE);INSERT INTO groups (title)SELECT DISTINCT group_name FROM students;ALTER TABLE students ADD COLUMN group_id INTEGER;UPDATE studentsSET group_id = (SELECT id FROM groups WHERE title = students.group_name);
