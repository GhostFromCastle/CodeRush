Ключи и ограничения

~30 минут Средний уровень Теория и Практика

База данных отличается от набора CSV-файлов не только языком запросов. Главное - она следит за правилами. Эти правила называются ограничениями, и они спасают от мусора в данных.

В этом уроке мы:

  • Разберём первичный и внешний ключи.
  • Освоим NOT NULL, UNIQUE, DEFAULT, CHECK.
  • Поймём, что происходит при удалении связанных строк.
  • Научимся читать ошибки ограничений.
Аналогия

Паспорт: уникальный номер (PRIMARY KEY), прописка ссылается на дом (FOREIGN KEY), без паспорта нельзя (NOT NULL).

PRIMARY KEY

Первичный ключ однозначно определяет строку. В таблице может быть только один первичный ключ, и он не может содержать NULL:

CREATE TABLE users (    id    INTEGER PRIMARY KEY,    name  TEXT NOT NULL,    email TEXT NOT NULL UNIQUE);

В SQLite INTEGER PRIMARY KEY автоматически становится автоинкрементным: если не указать значение, база подставит следующее число. В PostgreSQL для этого используют SERIAL или GENERATED ALWAYS AS IDENTITY, в MySQL - AUTO_INCREMENT.

Ключ может быть составным - из нескольких столбцов:

CREATE TABLE order_items (    order_id   INTEGER,    product_id INTEGER,    quantity   INTEGER NOT NULL,    PRIMARY KEY (order_id, product_id));

Такая пара уникальна: один товар не может встречаться в заказе дважды отдельными строками - вместо этого увеличивают quantity.

NOT NULL и DEFAULT

CREATE TABLE products (    id    INTEGER PRIMARY KEY,    title TEXT    NOT NULL,    price INTEGER NOT NULL DEFAULT 0,    stock INTEGER NOT NULL DEFAULT 0);

NOT NULL запрещает пустое значение. DEFAULT подставляет значение, если столбец не указан при вставке.

NULL - не пустая строка

'' (пустая строка) и NULL - разные вещи. NOT NULL пропустит пустую строку. Если пустые значения недопустимы, добавьте проверку: CHECK (TRIM(name) <> '').

UNIQUE

Запрещает повторяющиеся значения. В отличие от первичного ключа, уникальных ограничений может быть несколько:

CREATE TABLE users (    id    INTEGER PRIMARY KEY,    email TEXT NOT NULL UNIQUE,    phone TEXT UNIQUE);

При этом UNIQUE в большинстве СУБД разрешает несколько NULL: два пользователя без телефона - нормально, а два с одинаковым номером - нет.

CHECK

Проверка условия на уровне строки:

CREATE TABLE products (    id    INTEGER PRIMARY KEY,    title TEXT NOT NULL,    price INTEGER NOT NULL CHECK (price >= 0),    stock INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0));

Теперь попытка вставить отрицательную цену закончится ошибкой CHECK constraint failed. Это лучше, чем потом искать, почему сумма заказа отрицательная.

FOREIGN KEY

Внешний ключ связывает строку с другой таблицей и не даёт создать «заказ на несуществующего клиента»:

CREATE TABLE orders (    id          INTEGER PRIMARY KEY,    customer_id INTEGER NOT NULL,    price       INTEGER NOT NULL,    created_at  TEXT    NOT NULL DEFAULT CURRENT_DATE,    FOREIGN KEY (customer_id) REFERENCES users (id));

Теперь база проверит: значение customer_id должно существовать в users.id. Попытка вставить 999 при отсутствии такого пользователя даст FOREIGN KEY constraint failed.

Что делать при удалении

Если удалить пользователя, у которого есть заказы, возможны варианты. Поведение задаётся в ON DELETE:

ПравилоЧто произойдёт
RESTRICTУдаление запрещено, пока есть заказы (по умолчанию)
CASCADEУдалятся и все его заказы
SET NULLУ заказов customer_id станет NULL
NO ACTIONПроверка откладывается до конца операции
 
FOREIGN KEY (customer_id) REFERENCES users (id) ON DELETE CASCADE

Осторожно с каскадом. Удаление одного пользователя может унести тысячи заказов. В финансовых системах почти всегда выбирают RESTRICT, а данные «удаляют» логически - через столбец deleted_at.

Как читать ошибки ограничений

  • NOT NULL constraint failed: users.name - не передано обязательное поле.
  • UNIQUE constraint failed: users.email - такой email уже есть.
  • CHECK constraint failed: price >= 0 - значение нарушило правило.
  • FOREIGN KEY constraint failed - ссылка на несуществующую строку либо удаление, на которое есть ссылки.

Хорошая новость: эти ошибки - не поломка, а защита. Они означают, что база не дала сохранить некорректные данные.

Шпаргалка

  • PRIMARY KEY уникальный идентификатор
  • FOREIGN KEY ссылка на другую таблицу
  • NOT NULL обязательное поле
  • UNIQUE без повторов
  • CHECK правило для значения
  • ON DELETE CASCADE удалить связанные

Если что-то не работает

  • Не получается вставить строку. Проверьте NOT NULL и CHECK: скорее всего, одно из значений не проходит.
  • «UNIQUE constraint failed» при обновлении. Меняете email на уже существующий.
  • Не удаляется пользователь. На него ссылаются заказы, действует RESTRICT. Сначала решите, что делать с заказами.
  • Внешний ключ не проверяется. В SQLite он по умолчанию отключён - выполните PRAGMA foreign_keys = ON;.
  • «В базе два клиента с одним телефоном». Ограничение не поставили заранее, и приложение создало дубли. Чистка данных - отдельная большая работа, поэтому правила лучше задавать сразу.

Практика

Задача 1. Таблица с правилами

Создайте таблицу reviews: id, product_id (внешний ключ на products), rating от 1 до 5, comment (может быть пустым), created_at по умолчанию текущая дата.

Подсказка

Для рейтинга подойдёт CHECK (rating BETWEEN 1 AND 5), для даты - DEFAULT CURRENT_DATE, для связи - FOREIGN KEY (product_id) REFERENCES products(id).

Решение учителя 
CREATE TABLE reviews (    id         INTEGER PRIMARY KEY,    product_id INTEGER NOT NULL,    rating     INTEGER NOT NULL CHECK (rating BETWEEN 1 AND 5),    comment    TEXT,    created_at TEXT NOT NULL DEFAULT CURRENT_DATE,    FOREIGN KEY (product_id) REFERENCES products (id));
Задача 2. Проверьте защиту

Попробуйте нарушить каждое ограничение из задачи 1: поставить рейтинг 7, вставить отзыв на несуществующий товар, оставить product_id пустым. Запишите текст каждой ошибки.

Подсказка

Ошибки не надо исправлять - их надо прочитать. Каждая начинается с названия ограничения.

Решение учителя 
INSERT INTO reviews (product_id, rating) VALUES (1, 7);-- CHECK constraint failed: rating BETWEEN 1 AND 5INSERT INTO reviews (product_id, rating) VALUES (999, 5);-- FOREIGN KEY constraint failedINSERT INTO reviews (rating) VALUES (5);-- NOT NULL constraint failed: reviews.product_id
Задача 3. Каскад или запрет

Для интернет-магазина решите, какое правило удаления выбрать для отзывов и для заказов. Обоснуйте.

Подсказка

Отзывы без товара бессмысленны. Заказы - финансовые документы, их нельзя терять.

Решение учителя

Отзывы - ON DELETE CASCADE: товар удалили, отзывы о нём больше не нужны. Заказы - ON DELETE RESTRICT: пользователя с историей покупок удалять нельзя, только помечать архивным. Это стандартная практика в системах с деньгами.

Задача 4. Уникальный телефон

Запретите два одинаковых телефона в таблице users, не пересоздавая её.

Подсказка

На существующую таблицу можно добавить уникальный индекс.

Решение учителя 
CREATE UNIQUE INDEX idx_users_phone ON users (phone);
