CTE, представления и триггеры

~35 минут Продвинутый уровень Теория и Практика

Большие запросы читаются тяжело: вложенные подзапросы, повторяющиеся вычисления, длинные цепочки. CTE и представления позволяют разбить логику на именованные шаги - как функции в обычном коде.

В этом уроке мы:

  • Освоим WITH и несколько CTE в одном запросе.
  • Разберём рекурсивные запросы.
  • Научимся создавать представления.
  • Поймём, зачем нужны триггеры.
Аналогия

Черновик и готовая копия: VIEW пересобирается при каждом открытии, MATERIALIZED VIEW - распечатанная копия, которую нужно обновлять.

CTE: WITH

WITH totals AS (    SELECT        customer_id,        SUM(price) AS total    FROM orders    GROUP BY customer_id)SELECT *FROM totalsWHERE total > 50000;

Читается сверху вниз: сначала «посчитаем итоги по клиентам», потом «покажем крупных». То же самое можно записать подзапросом, но с именем понятнее.

Несколько CTE разделяются запятыми:

WITH totals AS (    SELECT customer_id, SUM(price) AS total    FROM orders    GROUP BY customer_id),big AS (    SELECT * FROM totals WHERE total > 50000)SELECT u.name, b.totalFROM big AS bJOIN users AS u ON u.id = b.customer_idORDER BY b.total DESC;

Второй CTE видит результат первого. Это похоже на конвейер.

CTE не всегда материализуется

В PostgreSQL до версии 12 CTE выполнялся отдельно и мог быть медленнее подзапроса. Сейчас планировщик обычно встраивает его. Если запрос с CTE неожиданно медленный - проверьте EXPLAIN.

Рекурсивный CTE

Позволяет обходить иерархии: категории с подкатегориями, сотрудников с подчинёнными, дерево комментариев.

WITH RECURSIVE tree AS (    -- база рекурсии: корневые категории    SELECT id, title, parent_id, 1 AS level    FROM categories    WHERE parent_id IS NULL    UNION ALL    -- шаг: присоединяем дочерние    SELECT c.id, c.title, c.parent_id, t.level + 1    FROM categories AS c    JOIN tree AS t ON c.parent_id = t.id)SELECT * FROM tree;

Первый SELECT задаёт стартовые строки. Второй выполняется снова и снова, пока не перестанет возвращать новые строки. Важно предусмотреть условие остановки - иначе запрос уйдёт в бесконечность.

Представления

Представление (VIEW) - сохранённый запрос, который выглядит как таблица:

CREATE VIEW customer_totals ASSELECT    u.id,    u.name,    COALESCE(SUM(o.price), 0) AS totalFROM users AS uLEFT JOIN orders AS o ON o.customer_id = u.idGROUP BY u.id, u.name;

Теперь можно писать:

SELECT * FROM customer_totals WHERE total > 50000;

Представление не хранит данные - оно выполняет запрос каждый раз. Зато:

  • сложная логика живёт в одном месте;
  • можно ограничить доступ: дать пользователю представление без чувствительных столбцов;
  • схема может меняться, а код приложения - нет.

Удалить: DROP VIEW customer_totals;

Триггеры

Триггер - код, который выполняется автоматически при вставке, изменении или удалении. Классический пример - обновление времени изменения:

CREATE TRIGGER products_updated_atAFTER UPDATE ON productsFOR EACH ROWBEGIN    UPDATE products    SET updated_at = CURRENT_TIMESTAMP    WHERE id = OLD.id;END;

В SQLite триггеры создаются так же, но тело пишут между BEGIN и END без изменения NEW.updated_at напрямую (в SQLite нет BEFORE UPDATE ... SET для NEW, поэтому используют AFTER UPDATE с дополнительным UPDATE).

Другой частый сценарий - журнал изменений:

CREATE TABLE audit_log (    id         INTEGER PRIMARY KEY,    table_name TEXT,    row_id     INTEGER,    action     TEXT,    changed_at TEXT DEFAULT CURRENT_TIMESTAMP);

Триггер на DELETE пишет туда строку с данными об удалении.

Триггеры - осторожно

Логика в триггерах невидима: разработчик делает INSERT, а происходят ещё пять действий. Отлаживать такое тяжело. Используйте триггеры для аудита и простых инвариантов, а бизнес-логику держите в приложении.

Материализованные представления

Обычное представление пересчитывается каждый раз. Материализованное хранит результат на диске и обновляется по команде:

CREATE MATERIALIZED VIEW sales_monthly ASSELECT STRFTIME('%Y-%m', created_at) AS month, SUM(price) AS revenueFROM ordersGROUP BY month;REFRESH MATERIALIZED VIEW sales_monthly;

Есть в PostgreSQL и Oracle. В MySQL и SQLite аналога нет - используют таблицу с периодическим пересчётом.

Шпаргалка

  • WITH name AS именованный подзапрос
  • WITH RECURSIVE обход иерархии
  • CREATE VIEW сохранить запрос
  • CREATE TRIGGER автодействие
  • MATERIALIZED VIEW кэш результата

Если что-то не работает

  • «no such table» в CTE. CTE существует только внутри одного запроса. Для повторного использования нужно представление.
  • Рекурсивный запрос не завершается. Нет условия остановки или данные содержат цикл.
  • VIEW медленное. Оно выполняет запрос каждый раз. Для тяжёлой аналитики используйте материализованное представление или таблицу-кэш.
  • Триггер не срабатывает. Проверьте момент (BEFORE / AFTER) и событие (INSERT / UPDATE / DELETE).
  • «VIEW стал тормозить на больших данных». Представление выполняет запрос каждый раз. Для тяжёлой аналитики делают материализованное представление или таблицу-кэш с пересчётом по расписанию.

Практика

Задача 1. Разбейте запрос

Перепишите запрос с вложенным подзапросом из урока про оконные функции (топ-2 заказа клиента) через CTE.

Подсказка

Вынесите SELECT с ROW_NUMBER в WITH ranked AS (...), затем снаружи WHERE rn <= 2.

Решение учителя 
WITH ranked AS (    SELECT        id,        customer_id,        price,        ROW_NUMBER() OVER (            PARTITION BY customer_id ORDER BY price DESC        ) AS rn    FROM orders)SELECT *FROM rankedWHERE rn <= 2;
Задача 2. Дерево категорий

Создайте таблицу categories с полем parent_id и заполните три уровня. Выведите дерево с уровнем вложенности через рекурсивный CTE.

Подсказка

База рекурсии - строки с parent_id IS NULL. Шаг - соединение c.parent_id = t.id и t.level + 1.

Решение учителя 
WITH RECURSIVE tree AS (    SELECT id, title, parent_id, 1 AS level    FROM categories    WHERE parent_id IS NULL    UNION ALL    SELECT c.id, c.title, c.parent_id, t.level + 1    FROM categories AS c    JOIN tree AS t ON c.parent_id = t.id)SELECT level, title FROM tree ORDER BY level, title;
Задача 3. Представление для отчёта

Создайте представление monthly_sales с выручкой по месяцам. Затем получите из него три лучших месяца.

Подсказка

CREATE VIEW monthly_sales AS SELECT ... GROUP BY month;, затем обычный SELECT ... ORDER BY revenue DESC LIMIT 3.

Решение учителя 
CREATE VIEW monthly_sales ASSELECT    STRFTIME('%Y-%m', created_at) AS month,    SUM(price) AS revenueFROM ordersGROUP BY month;SELECT * FROM monthly_salesORDER BY revenue DESCLIMIT 3;
Задача 4. Представление с топом

Создайте представление top_customers с тремя клиентами, потратившими больше всех, и выведите его.

Подсказка

Внутри представления используйте GROUP BY, ORDER BY и LIMIT 3.

Решение учителя 
CREATE VIEW top_customers ASSELECT    c.name,    SUM(o.price) AS totalFROM customers AS cJOIN orders AS o ON o.customer_id = c.idGROUP BY c.id, c.nameORDER BY total DESCLIMIT 3;SELECT * FROM top_customers;
