Транзакции и ACID

~35 минут Продвинутый уровень Теория и Практика

Представьте перевод денег между счетами. Он состоит из двух действий: списать с одного счёта и зачислить на другой. Если между ними что-то сломается, деньги исчезнут. Транзакции гарантируют, что такого не произойдёт.

В этом уроке мы:

  • Освоим BEGIN, COMMIT и ROLLBACK.
  • Разберём свойства ACID.
  • Поймём уровни изоляции и аномалии чтения.
  • Узнаем, что такое дедлок.
Аналогия

Банковский перевод: списать и зачислить - одно действие. Если посередине отключили свет, половины быть не должно.

Что такое транзакция

Транзакция - это группа операций, которая выполняется целиком или не выполняется вовсе.

BEGIN;UPDATE accounts SET balance = balance - 1000 WHERE id = 1;UPDATE accounts SET balance = balance + 1000 WHERE id = 2;COMMIT;

Если между BEGIN и COMMIT произойдёт ошибка или вы выполните ROLLBACK, оба изменения отменятся.

BEGIN;DELETE FROM orders WHERE customer_id = 5;-- передумалиROLLBACK;

ACID

Четыре свойства, которые отличают настоящую транзакционную базу от набора файлов:

  • Atomicity (атомарность). Всё или ничего. Не бывает перевода, где деньги списались, но не зачислились.
  • Consistency (согласованность). Транзакция переводит базу из одного корректного состояния в другое: ограничения и внешние ключи соблюдаются.
  • Isolation (изолированность). Параллельные транзакции не видят незавершённых изменений друг друга.
  • Durability (долговечность). После COMMIT данные переживут даже внезапное отключение питания.
Autocommit

По умолчанию большинство клиентов работает в режиме autocommit: каждая команда фиксируется сразу. Чтобы объединить несколько операций, транзакцию открывают явно через BEGIN. В SQLite команда BEGIN называется именно так, в MySQL можно писать START TRANSACTION.

SAVEPOINT

Внутри транзакции можно ставить точки сохранения и откатываться к ним:

BEGIN;INSERT INTO orders (customer_id, price) VALUES (1, 5000);SAVEPOINT after_order;INSERT INTO order_items (order_id, product_id, quantity) VALUES (1, 99, 1);ROLLBACK TO after_order;COMMIT;

Заказ останется, а неудавшаяся позиция - нет. Удобно в длинных операциях, где часть шагов можно смело отбросить.

Уровни изоляции

Когда две транзакции работают одновременно, возможны аномалии:

АномалияЧто происходит
Dirty readВидно изменение, которое ещё не зафиксировано
Non-repeatable readДва одинаковых чтения дают разные данные
Phantom readМежду чтениями появились новые строки

Уровни изоляции определяют, какие аномалии допустимы:

  • READ UNCOMMITTED - видны даже незафиксированные изменения. Почти не используется.
  • READ COMMITTED - по умолчанию в PostgreSQL. Dirty read исключён.
  • REPEATABLE READ - по умолчанию в MySQL. Повторное чтение той же строки даёт тот же результат.
  • SERIALIZABLE - максимальная строгость, транзакции ведут себя так, будто выполнялись по очереди. Медленнее.
BEGIN;SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;-- ...COMMIT;

Чем строже уровень, тем меньше аномалий и тем больше блокировок и ожиданий.

Блокировки и дедлок

При изменении строки база ставит блокировку. Пока транзакция не завершилась, другая не сможет изменить ту же строку.

Дедлок - ситуация, когда две транзакции ждут друг друга:

Транзакция A: заблокировала строку 1, ждёт строку 2Транзакция B: заблокировала строку 2, ждёт строку 1

База обнаруживает такое и откатывает одну из транзакций с ошибкой deadlock detected. Лечится порядком: всегда блокируйте строки в одном и том же порядке и держите транзакции короткими.

Практические правила

  • Короткие транзакции. Не держите открытую транзакцию, пока пользователь думает или идёт запрос к внешнему API.
  • Не ждите внутри транзакции. Сначала подготовьте данные, потом открывайте.
  • Обрабатывайте ошибки. При исключении обязательно ROLLBACK, иначе блокировки останутся висеть.
  • Одинаковый порядок. Это снижает риск дедлоков.

Шпаргалка

  • BEGIN начать транзакцию
  • COMMIT зафиксировать
  • ROLLBACK отменить
  • SAVEPOINT точка отката
  • ACID свойства транзакции
  • SERIALIZABLE строгий уровень изоляции

Если что-то не работает

  • Изменения «пропали». Транзакция не была зафиксирована. Проверьте, что вызывали COMMIT.
  • «database is locked». Другая транзакция держит блокировку. Найдите долгий процесс и завершите его.
  • «deadlock detected». Порядок блокировок разный. Упорядочьте операции.
  • ROLLBACK не сработал. В autocommit-режиме каждая команда уже зафиксирована - нужен явный BEGIN.
  • Транзакция висит после ошибки. В PostgreSQL после ошибки транзакция переходит в состояние aborted: нужен ROLLBACK перед продолжением.
  • «Деньги списались дважды». Пользователь дважды нажал кнопку, и два запроса прошли параллельно. Транзакция сама это не решит - нужна защита от повторной отправки (идемпотентность).

Практика

Задача 1. Перевод

Создайте таблицу accounts с двумя счетами по 10 000. Переведите 3 000 с первого на второй в транзакции. Проверьте итоговую сумму до и после.

Подсказка

Сумма всех балансов должна остаться 20 000. Если после перевода она другая - транзакция собрана неверно.

Решение учителя 
BEGIN;UPDATE accounts SET balance = balance - 3000 WHERE id = 1;UPDATE accounts SET balance = balance + 3000 WHERE id = 2;COMMIT;SELECT SUM(balance) AS total FROM accounts; -- 20000
Задача 2. Ошибка посередине

В той же транзакции после списания попробуйте зачислить деньги на несуществующий счёт. Что произойдёт с первым изменением? Проверьте через ROLLBACK.

Подсказка

Обновится 0 строк - ошибки не будет. Проверяйте количество затронутых строк, иначе транзакция «успешно» спишет деньги в никуда.

Решение учителя 
BEGIN;UPDATE accounts SET balance = balance - 3000 WHERE id = 1;-- счёт 999 не существует: обновится 0 строкUPDATE accounts SET balance = balance + 3000 WHERE id = 999;ROLLBACK;SELECT * FROM accounts; -- балансы не изменились

В реальном коде после UPDATE проверяют, что затронута хотя бы одна строка, и только тогда фиксируют транзакцию.

Задача 3. Точка сохранения

В одной транзакции добавьте заказ и две позиции. После первой позиции поставьте SAVEPOINT, вторую сделайте ошибочной и откатитесь к точке. Зафиксируйте транзакцию - должны остаться заказ и одна позиция.

Подсказка

ROLLBACK TO SAVEPOINT имя; отменяет только действия после точки, не всю транзакцию.

Решение учителя 
BEGIN;INSERT INTO orders (id, customer_id, price) VALUES (100, 1, 5000);INSERT INTO order_items (order_id, product_id, quantity) VALUES (100, 1, 1);SAVEPOINT after_first_item;INSERT INTO order_items (order_id, product_id, quantity) VALUES (100, 999, 1); -- ошибкаROLLBACK TO after_first_item;COMMIT;
Задача 4. Перевод с проверкой

Спишите 5000 со счёта 1 и зачислите на счёт 2. Если на первом недостаточно денег - откатите транзакцию.

Подсказка

Сначала UPDATE ... WHERE id = 1 AND balance >= 5000, затем проверьте, что обновилась строка.

Решение учителя 
BEGIN;UPDATE accountsSET balance = balance - 5000WHERE id = 1 AND balance >= 5000;-- если изменено 0 строк, откатываемсяROLLBACK;-- иначе-- UPDATE accounts SET balance = balance + 5000 WHERE id = 2;-- COMMIT;
