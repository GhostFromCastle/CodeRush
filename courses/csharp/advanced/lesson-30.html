Паттерны проектирования

~50 минут Продвинутый уровень Теория и Практика

До этого момента мы учились писать код: переменные, циклы, классы, generics, LINQ, асинхронность. Но вот в чём штука: писать код, который работает, и писать код, который удобно поддерживать - это две разные задачи. Одна и та же программа может быть написана так, что через месяц в ней никто не разберётся, а может - так, что новый разработчик поймёт структуру за час.

Опытные программисты давно заметили: одни и те же задачи встречаются снова и снова. Как организовать единственный экземпляр класса? Как создавать объекты, не привязываясь к конкретным классам? Как уведомить всех подписчиков об изменениях? Для всех этих вопросов уже придуманы готовые решения - паттерны проектирования.

Сегодня разберём четыре самых популярных: Singleton, Factory Method, Strategy и Observer. Это не «магия для избранных», а просто проверенные шаблоны, которые делают код понятнее и гибче.

Что такое паттерн проектирования

Паттерн проектирования - это готовое решение типовой задачи. Не библиотека, не фреймворк, а именно шаблон, описание того, как организовать классы и их взаимодействие. Вы как бы получаете чертёж, по которому уже много раз строили дома.

Аналогия со строительством. Если вы строите дом, вам не нужно каждый раз изобретать, как соединять балки или как делать лестницу. Есть проверенные архитектурные решения, которые работают веками. Вы берёте их и адаптируете под конкретный проект.

Паттерны делятся на три большие категории:

  • Порождающие (Creational) - как правильно создавать объекты. Примеры: Singleton, Factory Method, Builder, Prototype.
  • Структурные (Structural) - как правильно соединять классы между собой. Примеры: Adapter, Facade, Decorator, Proxy.
  • Поведенческие (Behavioral) - как правильно организовывать взаимодействие объектов. Примеры: Strategy, Observer, Command, State.
Важно: не переусердствуйте

Паттерны - это инструменты, а не цель. Если задача простая и решается в лоб - не нужно натягивать на неё три паттерна. Опытные программисты знают паттерны не для того, чтобы применять их везде, а чтобы узнавать ситуации, в которых они уместны.

Singleton: единственный экземпляр

Представьте, что в программе есть сущность, которая должна существовать в единственном экземпляре. Например, логгер, подключение к базе данных, конфигурация приложения. Если создать два логгера - они могут писать в один файл и конфликтовать. Если два подключения - они будут тратить ресурсы впустую.

Singleton (Одиночка) - это паттерн, который гарантирует, что класс имеет только один экземпляр, и предоставляет глобальную точку доступа к нему.

Аналогия: президент страны. В любой момент времени он один. К нему можно обратиться через официальные каналы, но создать «второго президента» невозможно.

Как это выглядит в C#

class Logger{    private static Logger instance;    private Logger() { }    public static Logger Instance    {        get        {            if (instance == null)            {                instance = new Logger();            }            return instance;        }    }    public void Log(string message)    {        Console.WriteLine($"[LOG] {message}");    }}

Разберём, как это работает:

  • private static Logger instance - статическое поле, которое хранит единственный экземпляр.
  • private Logger() { } - приватный конструктор. Это ключевой момент: снаружи нельзя написать new Logger().
  • public static Logger Instance - публичное свойство, через которое получают доступ. Оно создаёт экземпляр при первом обращении и потом возвращает тот же самый.

Используется так:

Logger.Instance.Log("Приложение запущено");Logger.Instance.Log("Пользователь вошёл");Logger.Instance.Log("Ошибка");

Сколько раз вы ни обращаетесь к Logger.Instance, вы всегда получаете один и тот же объект. Все записи попадают в одно место.

Потокобезопасный Singleton

Приведённый выше код хорош для однопоточных программ. Но если два потока одновременно обратятся к Instance в первый раз, могут создаться два экземпляра. Это называется race condition. Чтобы избежать проблемы, используют блокировку:

class Logger{    private static Logger instance;    private static readonly object lockObj = new object();    private Logger() { }    public static Logger Instance    {        get        {            lock (lockObj)            {                if (instance == null)                {                    instance = new Logger();                }                return instance;            }        }    }}

Но и это не идеально: lock выполняется при каждом обращении, что замедляет работу. Самый элегантный вариант - использовать статический конструктор, который сам по себе потокобезопасен:

class Logger{    private static readonly Logger instance = new Logger();    static Logger() { }    private Logger() { }    public static Logger Instance    {        get { return instance; }    }}

Здесь экземпляр создаётся один раз при первом обращении к классу и больше не меняется. Такой подход называется thread-safe lazy initialization и считается одним из лучших.

Осторожно с Singleton

Singleton - самый критикуемый паттерн. Его часто используют там, где не нужно, и это делает код негибким и сложным для тестирования. В современном C# для тех же задач часто используют внедрение зависимостей (Dependency Injection), о котором мы поговорим позже. Но понимать Singleton нужно - он лежит в основе многих фреймворков.

Factory Method: фабрика объектов

Представьте, что вы пишете игру и вам нужно создавать разных врагов. Есть гоблины, скелеты, драконы. Прямо в коде игры вы бы писали new Goblin(), new Skeleton() и так далее. Но что, если враги добавляются в игру динамически? Или нужна возможность включать и отключать типы врагов из конфигурации?

Factory Method (Фабричный метод) - это паттерн, который выносит создание объектов в отдельный класс-фабрику. Клиентский код не знает, какой именно класс создаётся - он просто просит «дай мне врага такого-то типа», а фабрика решает, что вернуть.

Аналогия: ресторан. Вы говорите «принесите мне пиццу» - и кухня решает, как её приготовить. Вам неважно, кто именно печёт, на какой печи и в какой последовательности кладёт ингредиенты. Вы получаете готовое блюдо.

Пример с животными

Сначала определим общий интерфейс:

interface IAnimal{    void Speak();}class Dog : IAnimal{    public void Speak()    {        Console.WriteLine("Гав!");    }}class Cat : IAnimal{    public void Speak()    {        Console.WriteLine("Мяу!");    }}

Теперь создадим фабрику, которая умеет создавать этих животных по строковому имени:

class AnimalFactory{    public static IAnimal Create(string type)    {        if (type == "dog")        {            return new Dog();        }        if (type == "cat")        {            return new Cat();        }        return null;    }}

Клиентский код теперь не знает ни про Dog, ни про Cat:

IAnimal pet = AnimalFactory.Create("dog");pet.Speak();IAnimal pet2 = AnimalFactory.Create("cat");pet2.Speak();

Что это даёт?

  • Гибкость. Если завтра нужно добавить Cow, меняется только фабрика. Клиентский код остаётся прежним.
  • Единая точка создания. Вся логика создания объектов - в одном месте. Легче поддерживать.
  • Скрытие сложности. Если создание объекта требует 10 шагов - это спрятано внутри фабрики.

В реальной жизни Factory используется повсеместно: создание подключений к базе данных, HTTP-клиентов, парсеров, обработчиков. Именно так работают многие фреймворки - вы просите объект, а фреймворк решает, какой класс вам вернуть.

Strategy: разные алгоритмы для одной задачи

Представьте, что вы пишете интернет-магазин. У вас есть три способа оплаты: картой, наличными при получении, электронным кошельком. Логика оплаты разная, но сам процесс оформления заказа одинаковый: подтвердить заказ, списать деньги, отправить чек.

Как быть? Можно засунуть всё в один метод с кучей if-else. Но когда способов станет десять, этот метод превратится в монстра. И если в одном месте ошибётесь - сломаете все способы сразу.

Strategy (Стратегия) - это паттерн, который выносит каждый алгоритм в отдельный класс с общим интерфейсом. Клиент выбирает нужную стратегию в зависимости от ситуации.

Аналогия с навигатором. Вы едете в незнакомый город. Можно ехать на машине, на автобусе, на велосипеде, пешком. Цель одна - добраться до точки, но способы разные. Вы выбираете тот, который удобнее сейчас.

Пример с оплатой

Сначала определим общий интерфейс стратегии:

interface IPaymentStrategy{    void Pay(int amount);}

Теперь три конкретные реализации:

class CardPayment : IPaymentStrategy{    public void Pay(int amount)    {        Console.WriteLine($"Оплата картой: {amount} руб");    }}class CashPayment : IPaymentStrategy{    public void Pay(int amount)    {        Console.WriteLine($"Оплата наличными: {amount} руб");    }}class WalletPayment : IPaymentStrategy{    public void Pay(int amount)    {        Console.WriteLine($"Оплата кошельком: {amount} руб");    }}

И класс Order, который использует стратегию:

class Order{    private IPaymentStrategy strategy;    public void SetPaymentStrategy(IPaymentStrategy s)    {        strategy = s;    }    public void Checkout(int amount)    {        strategy.Pay(amount);    }}

Использование:

Order order = new Order();order.SetPaymentStrategy(new CardPayment());order.Checkout(1500);order.SetPaymentStrategy(new CashPayment());order.Checkout(2000);

Обратите внимание: класс Order вообще не знает, как именно происходит оплата. Он просто вызывает Pay у стратегии. Если завтра добавится новый способ оплаты - нужно написать новый класс и передать его в SetPaymentStrategy. Order не изменится.

Чем это лучше if-else

Сравните два подхода. Без Strategy:

public void Checkout(int amount, string type){    if (type == "card")    {        // 20 строк кода оплаты картой    }    else if (type == "cash")    {        // 20 строк кода оплаты наличными    }    else if (type == "wallet")    {        // 20 строк кода оплаты кошельком    }}

С Strategy - три маленьких класса, каждый со своей логикой. Тестировать легче, читать легче, добавлять новые способы - легко. Это и есть сила паттерна.

Observer: подписка на изменения

Представьте, что вы подписаны на новостной канал в Telegram. Как только появляется новый пост - вам приходит уведомление. Вы не проверяете канал каждую минуту вручную, канал сам «толкает» вам новость.

Observer (Наблюдатель) - это паттерн, где объект-издатель уведомляет всех подписчиков об изменениях своего состояния. Между издателем и подписчиками нет жёсткой связи: издатель не знает, кто именно на него подписан.

Аналогия: газета и подписчики. Газета выпускает новый номер - и все, кто подписан, получают его. Газете неважно, кто эти люди и сколько их. Главное - список подписчиков.

Пример с новостным каналом

Интерфейс подписчика:

interface IObserver{    void Update(string news);}

Конкретный подписчик:

class Subscriber : IObserver{    private string name;    public Subscriber(string name)    {        this.name = name;    }    public void Update(string news)    {        Console.WriteLine($"{name} получил: {news}");    }}

Издатель, который умеет добавлять и удалять подписчиков, а также рассылать им новости:

class NewsChannel{    private List<IObserver> subscribers = new List<IObserver>();    public void Subscribe(IObserver observer)    {        subscribers.Add(observer);    }    public void Unsubscribe(IObserver observer)    {        subscribers.Remove(observer);    }    public void Publish(string news)    {        foreach (var s in subscribers)        {            s.Update(news);        }    }}

Использование:

NewsChannel channel = new NewsChannel();channel.Subscribe(new Subscriber("Алексей"));channel.Subscribe(new Subscriber("Мария"));channel.Publish("Вышел новый урок по C#!");

Когда вызывается Publish, все подписчики получают уведомление. Алексей и Мария увидят сообщение. Если добавить третьего подписчика - он тоже начнёт получать новости автоматически.

Где это используется

Observer - один из самых распространённых паттернов. Он лежит в основе:

  • Обработчиков событий (button.Click += ...) - кнопка не знает, кто на неё подписан, но уведомляет всех при нажатии.
  • Реактивных интерфейсов - когда изменение модели данных автоматически обновляет отображение.
  • Систем обмена сообщениями - брокеров, pub/sub-очередей.
  • Событий в C# - ключевое слово event это именно реализация Observer на уровне языка.
Связь с делегатами

В уроке 23 мы разбирали делегаты Action и Func. Observer в C# часто реализуется именно через них: список делегатов вместо списка IObserver. Встроенный тип event работает именно так.

Шпаргалка

Самое важное в одном месте:

  • Паттерн готовое решение типовой задачи
  • Порождающие как создавать объекты
  • Структурные как соединять классы
  • Поведенческие как взаимодействуют объекты
  • Singleton единственный экземпляр
  • Factory единая точка создания объектов
  • Strategy взаимозаменяемые алгоритмы
  • Observer подписка на изменения

Если что-то не работает

Разберём типичные проблемы и заблуждения при работе с паттернами.

  • «Паттерны - это обязательно, без них плохой код». Нет. Паттерны - это инструменты. Если задача решается в две строчки без паттернов - не натягивайте на неё Singleton и Strategy. Переусложнение хуже, чем простота.
  • «Singleton - плохой паттерн, никогда не используйте». Это крайность. У Singleton есть проблемы с тестированием и со скрытыми зависимостями, но в некоторых сценариях он уместен - например, для логгеров, конфигурации, кешей. Важно понимать, где он вредит, а где помогает.
  • «Factory - это просто if-else, обёрнутый в класс». По сути - да, но вынос этого if-else в отдельное место даёт много плюсов: гибкость, единую точку изменения, читаемость. Клиентский код больше не думает про то, как создаётся объект.
  • «Strategy - это то же самое, что и полиморфизм». Strategy - это применение полиморфизма для конкретной задачи. Полиморфизм - механизм языка, Strategy - паттерн, который его использует для выбора алгоритма.
  • «Observer слишком сложный, лучше просто вызвать все методы вручную». Если подписчиков 2-3 и они не меняются - возможно. Но когда их десятки и они добавляются динамически, Observer незаменим. Плюс он убирает жёсткую связь между издателем и подписчиками.
  • «Я не знаю паттернов - значит, я плохой программист». Ничего подобного. Паттерны приходят с опытом. Начинающему важнее освоить базу - классы, наследование, интерфейсы. Паттерны - следующий уровень. И вы его только что прошли.

Если что-то не получается - напишите нам в Telegram, разберёмся вместе.

Практика

Четыре задачи по возрастающей сложности. У каждой есть подсказка и решение учителя.

Задача 1. Свой Singleton

Создайте класс ConfigManager, который хранит настройки приложения в виде словаря Dictionary<string, string>. Класс должен быть Singleton: единственный экземпляр, доступный через свойство Instance. Добавьте методы Set(key, value) и Get(key).

Подсказка

Используйте приватный конструктор и статическое поле для экземпляра. Словарь объявите как поле класса и инициализируйте в конструкторе. Свойство Instance возвращает статический экземпляр.

Решение учителя 
class ConfigManager{    private static readonly ConfigManager instance = new ConfigManager();    private Dictionary<string, string> settings;    static ConfigManager() { }    private ConfigManager()    {        settings = new Dictionary<string, string>();    }    public static ConfigManager Instance    {        get { return instance; }    }    public void Set(string key, string value)    {        settings[key] = value;    }    public string Get(string key)    {        return settings.ContainsKey(key) ? settings[key] : null;    }}static void Main(string[] args){    ConfigManager.Instance.Set("theme", "dark");    Console.WriteLine(ConfigManager.Instance.Get("theme"));}
Задача 2. Фабрика документов

Создайте интерфейс IDocument с методом Open() и две реализации: PdfDocument и WordDocument. Напишите фабрику DocumentFactory, которая по расширению файла (.pdf, .docx) создаёт нужный документ.

Подсказка

Метод фабрики Create(string extension) должен вернуть IDocument. Внутри - проверка расширения и создание соответствующего объекта. Если расширение неизвестно - верните null или бросьте исключение.

Решение учителя 
interface IDocument{    void Open();}class PdfDocument : IDocument{    public void Open()    {        Console.WriteLine("Открыт PDF-документ");    }}class WordDocument : IDocument{    public void Open()    {        Console.WriteLine("Открыт Word-документ");    }}class DocumentFactory{    public static IDocument Create(string ext)    {        if (ext == ".pdf")        {            return new PdfDocument();        }        if (ext == ".docx")        {            return new WordDocument();        }        return null;    }}static void Main(string[] args){    IDocument doc = DocumentFactory.Create(".pdf");    doc.Open();}
Задача 3. Стратегия сортировки

Создайте интерфейс ISortStrategy с методом Sort(int[] arr). Реализуйте две стратегии: BubbleSort и QuickSort (или просто Array.Sort внутри). Класс Sorter принимает стратегию и сортирует массив выбранным способом.

Подсказка

Класс Sorter хранит поле типа ISortStrategy. Метод SetStrategy позволяет менять её на лету. Метод DoSort(int[] arr) вызывает strategy.Sort(arr). В реализациях можно использовать простую сортировку пузырьком и Array.Sort.

Решение учителя 
interface ISortStrategy{    void Sort(int[] arr);}class BubbleSort : ISortStrategy{    public void Sort(int[] arr)    {        for (int i = 0; i < arr.Length; i++)        {            for (int j = 0; j < arr.Length - 1 - i; j++)            {                if (arr[j] > arr[j + 1])                {                    int temp = arr[j];                    arr[j] = arr[j + 1];                    arr[j + 1] = temp;                }            }        }        Console.WriteLine("Отсортировано пузырьком");    }}class QuickSort : ISortStrategy{    public void Sort(int[] arr)    {        Array.Sort(arr);        Console.WriteLine("Отсортировано быстро");    }}class Sorter{    private ISortStrategy strategy;    public void SetStrategy(ISortStrategy s)    {        strategy = s;    }    public void DoSort(int[] arr)    {        strategy.Sort(arr);    }}
Задача 4. Наблюдатель за температурой

Реализуйте паттерн Observer для датчика температуры. Класс Thermometer хранит текущую температуру и позволяет подписчикам получать уведомления при каждом изменении. Создайте два подписчика: Display (показывает значение) и Alarm (срабатывает, если температура выше 30 градусов).

Подсказка

Интерфейс ITemperatureObserver с методом OnTemperatureChanged(int temp). В Thermometer список подписчиков и метод SetTemperature(int temp), который сохраняет значение и вызывает OnTemperatureChanged у всех подписчиков.

Решение учителя 
interface ITemperatureObserver{    void OnTemperatureChanged(int temp);}class Display : ITemperatureObserver{    public void OnTemperatureChanged(int temp)    {        Console.WriteLine($"Температура: {temp}°C");    }}class Alarm : ITemperatureObserver{    public void OnTemperatureChanged(int temp)    {        if (temp > 30)        {            Console.WriteLine("ВНИМАНИЕ! Перегрев!");        }    }}class Thermometer{    private List<ITemperatureObserver> observers = new List<ITemperatureObserver>();    private int temperature;    public void Subscribe(ITemperatureObserver o)    {        observers.Add(o);    }    public void SetTemperature(int temp)    {        temperature = temp;        foreach (var o in observers)        {            o.OnTemperatureChanged(temperature);        }    }}static void Main(string[] args){    Thermometer t = new Thermometer();    t.Subscribe(new Display());    t.Subscribe(new Alarm());    t.SetTemperature(25);    t.SetTemperature(35);}

Что мы узнали и что дальше

Сегодня мы прикоснулись к искусству архитектуры кода. Узнали, что такое паттерны проектирования, зачем они нужны и как делятся на три категории: порождающие, структурные и поведенческие.

Разобрали четыре самых популярных паттерна:

  • Singleton - когда нужен единственный экземпляр класса: логгер, конфигурация, кеш.
  • Factory Method - единая точка создания объектов, скрывающая детали от клиентского кода.
  • Strategy - взаимозаменяемые алгоритмы под общим интерфейсом: способы оплаты, сортировки, сжатия.
  • Observer - подписка на изменения: события, уведомления, реактивные интерфейсы.

Поняли главное: паттерны - это не цель, а инструмент. Применять их нужно там, где они действительно решают проблему, а не везде подряд. Переусложнённый код с десятью паттернами хуже, чем простой код без них.

Эти четыре паттерна - только начало. Всего их десятки, но запоминать все сразу не нужно. Постепенно, по мере роста опыта, вы будете узнавать новые ситуации и новые паттерны для них.

В следующем уроке мы займёмся рефакторингом - искусством улучшать код, не меняя его поведение. Разберёмся, как находить «плохие места» в существующем коде, как превращать длинные методы в короткие, как убирать дублирование и как делать код читаемым. Это тот навык, который отличает код, в котором приятно работать, от кода, в котором хочется всё переписать с нуля.
