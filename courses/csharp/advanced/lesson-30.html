Юнит-тестирование

~45 минут Продвинутый уровень Теория и Практика

Представьте, что вы пишете калькулятор. Всё работает: 2 + 2 = 4, 10 - 3 = 7. Вы довольны, отдаёте заказчику. А через неделю выясняется, что при делении на ноль программа падает, а если ввести отрицательное число - показывает ерунду. Пользователи злятся, заказчик в ярости, вы правите код в спешке и в процессе ломаете что-то ещё.

Этой ситуации можно было избежать. Именно для этого существует юнит-тестирование - практика, при которой каждая маленькая часть программы (метод, функция) проверяется автоматическими тестами. Тестами, которые вы запускаете одной командой за доли секунды и сразу видите: всё работает или что-то сломалось.

Что такое юнит-тест

Юнит (от английского unit - «единица») - это самая маленькая логическая единица кода. Обычно - один метод. Юнит-тест - это программа, которая вызывает этот метод с определёнными входными данными и проверяет, что результат совпадает с ожидаемым.

Аналогия: представьте, что вы собираете автомобиль. Юнит-тесты - это проверка каждой детали отдельно на стенде: работает ли двигатель, крутятся ли колёса, загораются ли фары. Прежде чем собрать весь автомобиль и поехать, вы убедились, что каждая деталь исправна. Если что-то не так - вы сразу знаете, что именно.

Без тестов проверка выглядит так: собрали всю машину, завели, поехали - что-то скрипит. А что именно? Двигатель? Подвеска? Коробка передач? Приходится всё разбирать и искать наугад.

Главная идея

Юнит-тест - это код, который проверяет другой код. Вы пишете его один раз, а запускаете сотни раз в процессе разработки. И каждый раз он отвечает на один вопрос: «Этот метод всё ещё работает так, как должен?». Если да - все тесты зелёные. Если что-то сломалось - тест краснеет, и вы сразу знаете, где искать.

Зачем это нужно

Многие новички думают, что тесты - это «лишняя работа, которую навязывают сеньоры». На самом деле тесты экономят время и нервы. Вот реальные сценарии:

  • Рефакторинг без страха. Помните урок 27? Вы хотите улучшить код, но боитесь что-то сломать. С тестами этот страх исчезает: после каждого изменения запускаете тесты. Все зелёные - ничего не сломали.
  • Добавление новой функции. Нужно добавить новый способ оплаты, не затронув существующие? Тесты покажут, что старые способы по-прежнему работают.
  • Поиск багов. Пришёл баг-репорт: «При пустом списке программа падает». Вы пишете тест, который воспроизводит ситуацию. Смотрите - тест красный, баг подтверждён. Правите код, пока тест не станет зелёным. Теперь баг гарантированно не вернётся.
  • Документация. Тесты - это лучшая документация. Открыли тест-файл, посмотрели - сразу видно, как работает метод и какие входные данные он ожидает.
  • Уверенность при сдаче проекта. Не «я думаю, всё работает», а «я проверил 50 тестов, все проходят».

Фреймворк xUnit

В мире .NET есть несколько популярных фреймворков для тестирования: NUnit, MSTest и xUnit. xUnit - современный стандарт, его используют в ASP.NET Core, в большинстве open-source проектов и во многих компаниях. На нём и остановимся.

Юнит-тесты обычно живут в отдельном проекте, а не в основном. Это логично: тестовый код не должен попадать в релизную сборку. Структура типичного решения выглядит так:

MyApp/              <- основной проект (классы, логика)MyApp.Tests/        <- тестовый проект (юнит-тесты)MyApp.sln           <- файл решения

Чтобы создать тестовый проект, в Visual Studio нужно выбрать тип «xUnit Test Project», а через консоль - выполнить:

dotnet new xunit -o MyApp.Tests

И добавить ссылку на основной проект:

dotnet add reference ../MyApp/MyApp.csproj

Теперь в тестовом проекте можно ссылаться на классы из основного.

Схема Arrange-Act-Assert

Любой хороший юнит-тест строится по одной и той же схеме из трёх шагов. Запомните её: AAA - Arrange, Act, Assert.

  • Arrange (подготовка) - создать все объекты и входные данные, которые нужны для теста.
  • Act (действие) - вызвать тестируемый метод с подготовленными данными.
  • Assert (проверка) - убедиться, что результат совпадает с ожидаемым.

Давайте напишем первый тест. Сначала - код, который будем тестировать:

public class Calculator{    public int Add(int a, int b)    {        return a + b;    }    public int Divide(int a, int b)    {        if (b == 0)            throw new DivideByZeroException();        return a / b;    }}

И тест для метода Add:

using Xunit;public class CalculatorTests{    [Fact]    public void Add_TwoPositiveNumbers_ReturnsSum()    {        // Arrange        var calculator = new Calculator();        int a = 2;        int b = 3;        // Act        int result = calculator.Add(a, b);        // Assert        Assert.Equal(5, result);    }}

Разберём, что здесь важно:

  • [Fact] - атрибут, который говорит xUnit: «Это тест, запусти его». Без него метод просто не будет вызван.
  • Имя теста - Add_TwoPositiveNumbers_ReturnsSum. Соглашение об именовании: Метод_Условие_Ожидание. Глядя на имя, сразу понятно, что проверяется.
  • Assert.Equal - проверка, что первое значение равно второму. Если не равно - тест падает с сообщением, где именно ошибка.
Комментарии в тестах

Обычно в коде мы избегаем комментариев, но в тестах пометки // Arrange, // Act, // Assert - это стандарт индустрии. Они помогают читать тест и видны всем разработчикам. Это редкое исключение, где комментарии уместны.

Основные Assert-методы

Assert - это набор методов для проверки. Вот самые полезные:

  • Assert.Equal(expected, actual) - проверяет, что два значения равны. Работает с числами, строками, объектами и коллекциями.
  • Assert.NotEqual(a, b) - проверяет, что значения не равны.
  • Assert.True(condition) - проверяет, что условие истинно.
  • Assert.False(condition) - что ложно.
  • Assert.Null(obj) - что объект равен null.
  • Assert.NotNull(obj) - что не равен.
  • Assert.Contains(item, collection) - что коллекция содержит элемент.
  • Assert.Throws<T>(action) - что вызов метода выбрасывает определённое исключение.

Пример с проверкой исключения:

[Fact]public void Divide_ByZero_ThrowsException(){    // Arrange    var calculator = new Calculator();    // Act & Assert    Assert.Throws<DivideByZeroException>(() => calculator.Divide(10, 0));}

Метод Assert.Throws принимает лямбда-выражение и проверяет, что при его выполнении выбрасывается именно указанное исключение. Если исключение не выброшено или выброшено другое - тест падает.

Теории: много тестов в одном

Что, если нужно проверить один и тот же метод на разных входных данных? Например, Add для положительных, отрицательных, нулей, больших чисел. Писать десять почти одинаковых тестов - скучно и неэффективно.

Для этого в xUnit есть атрибут [Theory] в паре с [InlineData]:

[Theory][InlineData(2, 3, 5)][InlineData(-1, 1, 0)][InlineData(0, 0, 0)][InlineData(100, 200, 300)]public void Add_VariousInputs_ReturnsCorrectSum(int a, int b, int expected){    var calculator = new Calculator();    int result = calculator.Add(a, b);    Assert.Equal(expected, result);}

Что здесь происходит:

  • [Theory] - помечает метод как параметризованный тест.
  • [InlineData] - набор входных данных для одного прогона. Можно указать много таких атрибутов.
  • Метод принимает параметры a, b, expected - по числу значений в InlineData.

В Test Explorer вы увидите не один тест, а четыре отдельных прогона. Если один из них упадёт, вы сразу узнаете, какие именно входные данные вызвали проблему.

Граничные случаи: ищем баги

Самое ценное в тестах - это проверка граничных случаев. Именно там чаще всего прячутся баги. Начинающие разработчики обычно проверяют «нормальную» работу, но забывают про крайности. А зря.

Для любого метода полезно проверять:

  • Ноль. Что будет с 0? Ноль - это отдельный случай почти везде.
  • Отрицательные числа. Метод работает только с положительными? А что если передать отрицательное?
  • Пустые коллекции. Что делает метод с пустым массивом? Не падает ли?
  • Границы диапазонов. Если допустимы значения от 0 до 100, проверьте 0, 100, -1 и 101.
  • Null. Метод принимает объект - что будет, если передать null?
  • Очень большие значения. int.MaxValue, миллион записей, гигабайтная строка.

Пример: тестируем метод расчёта скидки, который возвращает скидку в процентах для суммы покупки.

public int CalculateDiscount(decimal amount){    if (amount < 1000) return 0;    if (amount < 5000) return 5;    return 10;}

Хороший набор тестов:

[Theory][InlineData(0, 0)]          // Ноль[InlineData(999, 0)]        // Рядом с границей снизу[InlineData(1000, 5)]       // Сама граница[InlineData(1001, 5)]       // Рядом с границей сверху[InlineData(4999, 5)]       // Рядом со второй границей[InlineData(5000, 10)]      // Вторая граница[InlineData(1000000, 10)]   // Большое значениеpublic void CalculateDiscount_Boundaries_ReturnsCorrectPercentage(decimal amount, int expected){    var calculator = new DiscountCalculator();    int result = calculator.CalculateDiscount(amount);    Assert.Equal(expected, result);}

Видите, как много граничных случаев? Именно такие тесты ловят баги, которые не видны при «обычной» проверке.

Что такое моки

Иногда тестируемый метод зависит от внешних вещей: базы данных, HTTP-запросов, файловой системы. В юнит-тесте мы не хотим трогать настоящую базу данных. Это медленно, требует настройки, а иногда опасно (что если тест запишет что-то в продакшн-базу?).

Для таких случаев используют моки (от английского mock - «имитация»). Мок - это поддельный объект, который ведёт себя как настоящий, но возвращает заранее заданные данные. В C# для этого чаще всего используют библиотеку Moq.

Аналогия: когда пилоты тренируются на симуляторе, они работают не с настоящим самолётом, а с имитацией. Симулятор ведёт себя как настоящий самолёт, но если вы разобьётесь - ничего страшного не произойдёт. Мок - это такой симулятор для кода.

Пример: тестируем сервис, который получает пользователя из базы и возвращает его имя в верхнем регистре.

public interface IUserRepository{    User GetById(int id);}public class UserService{    private readonly IUserRepository repo;    public UserService(IUserRepository repository)    {        repo = repository;    }    public string GetUserNameInUpperCase(int id)    {        User user = repo.GetById(id);        return user?.Name?.ToUpper();    }}

Тест с моком:

using Moq;[Fact]public void GetUserNameInUpperCase_ReturnsUpperCaseName(){    // Arrange    var mockRepo = new Mock<IUserRepository>();    mockRepo.Setup(r => r.GetById(1))        .Returns(new User { Name = "alexey" });    var service = new UserService(mockRepo.Object);    // Act    string result = service.GetUserNameInUpperCase(1);    // Assert    Assert.Equal("ALEXEY", result);}

Что произошло:

  • new Mock<IUserRepository>() - создали поддельный репозиторий, который выглядит как настоящий, но ничего не делает.
  • Setup(r => r.GetById(1)).Returns(...) - сказали моку: «Когда тебя попросят пользователя с id=1, верни вот этот объект».
  • mockRepo.Object - это и есть поддельный объект, который можно передать в UserService.

Тест работает мгновенно, ничего не пишет в реальную базу данных и не зависит от состояния внешнего мира. Мок - мощный инструмент для изоляции тестов.

Moq нужно установить

В отличие от xUnit, Moq - сторонняя библиотека. Она не идёт в комплекте с .NET. Установить её можно через NuGet:

dotnet add package Moq

Или в Visual Studio через «Manage NuGet Packages» у тестового проекта.

Сколько тестов писать

Единого ответа нет. Но есть несколько принципов, которыми пользуются опытные разработчики:

  • Тестируйте важную логику. Расчёты, бизнес-правила, алгоритмы - обязательно. Геттеры и сеттеры свойств - не нужно.
  • Проверяйте граничные случаи. Ноль, отрицательные числа, пустые коллекции, null.
  • Один тест - одна проверка. Не смешивайте проверку нескольких сценариев в одном тесте. Если упадёт - непонятно, что именно сломалось.
  • Тесты должны быть быстрыми. Весь набор - за секунды, не минуты. Если тесты медленные - их не будут запускать.
  • Тесты должны быть независимыми. Результат одного не должен влиять на другой. Не используйте общее состояние между тестами.

Хорошая практика - покрытие около 70-80% для важной логики. Стремиться к 100% обычно бессмысленно: часть кода (например, тривиальные геттеры) тестировать не нужно, а время тратится.

Шпаргалка

Самое важное в одном месте:

  • Юнит-тест проверка одного метода
  • xUnit современный фреймворк тестирования
  • AAA Arrange, Act, Assert
  • [Fact] одиночный тест
  • [Theory] + [InlineData] тест с разными данными
  • Assert.Equal проверка равенства
  • Assert.Throws проверка исключения
  • Moq поддельные зависимости

Если что-то не работает

Разберём типичные проблемы при работе с юнит-тестами.

  • «Тест не находится в Test Explorer». Проверьте: есть ли атрибут [Fact] или [Theory], публичный ли класс (с ключевым словом public), публичный ли метод, есть ли ссылка на пакет xUnit.
  • «Не могу обратиться к классу из основного проекта». Нужно добавить ссылку через dotnet add reference. В Visual Studio - правой кнопкой по тестовому проекту → Add → Project Reference.
  • «Тест падает, но я не понимаю почему». Смотрите сообщение об ошибке. xUnit выводит ожидаемое и фактическое значения. Если этого мало - используйте Assert.Equal с кастомным сообщением: Assert.Equal(expected, actual) - в выводе увидите оба значения.
  • «Тесты работают в одном порядке, но падают в другом». Тесты должны быть независимы друг от друга. Если один тест меняет общее состояние (статическое поле, файл, базу) - другой может упасть. Каждый тест должен быть самодостаточным.
  • «Тест проходит случайно». Возможно, вы тестируете что-то, что зависит от времени, случайных чисел или порядка выполнения. Тесты должны быть детерминированными: один и тот же код с одними и теми же данными всегда даёт один и тот же результат.
  • «Не хочу писать тесты, это долго». Первые пару раз - да. Но после 10-20 тестов вы поймёте шаблон, и на написание теста будет уходить минута. А экономить он будет часы отладки.
  • «У меня 100% покрытие, но всё равно есть баги». Покрытие показывает, какой код запускался тестами, но не гарантирует, что все сценарии проверены. Тесты на «нормальный» сценарий не ловят баги на граничных случаях. Думайте о тестах как о сценариях, а не о покрытии.

Если что-то не получается - напишите нам в Telegram, разберёмся вместе.

Практика

Четыре задачи по возрастающей сложности. У каждой есть подсказка и решение учителя.

Задача 1. Первый тест

Дан класс StringHelper с методом Reverse(string s), который переворачивает строку. Напишите юнит-тест, который проверяет, что Reverse("hello") возвращает "olleh". Используйте схему Arrange-Act-Assert и атрибут [Fact].

Подсказка

Структура: создайте объект StringHelper (Arrange), вызовите Reverse("hello") (Act), проверьте результат через Assert.Equal("olleh", result) (Assert).

Решение учителя 
using Xunit;public class StringHelperTests{    [Fact]    public void Reverse_SimpleWord_ReturnsReversed()    {        // Arrange        var helper = new StringHelper();        // Act        string result = helper.Reverse("hello");        // Assert        Assert.Equal("olleh", result);    }}
Задача 2. Граничные случаи

Для того же метода Reverse напишите тесты, которые проверяют граничные случаи: пустая строка, строка из одного символа, строка-палиндром (читается одинаково в обе стороны), строка с пробелами.

Подсказка

Используйте [Theory] и [InlineData], чтобы не писать отдельный тест на каждый случай. Например: [InlineData("", "")], [InlineData("a", "a")], [InlineData("шалаш", "шалаш")].

Решение учителя 
[Theory][InlineData("", "")][InlineData("a", "a")][InlineData("шалаш", "шалаш")][InlineData("hello world", "dlrow olleh")][InlineData("12345", "54321")]public void Reverse_VariousInputs_ReturnsReversed(string input, string expected){    var helper = new StringHelper();    string result = helper.Reverse(input);    Assert.Equal(expected, result);}

Обратите внимание: одним методом проверили пять разных сценариев. Если один из них сломается - xUnit покажет, какой именно.

Задача 3. Проверка исключения

Дан класс AgeValidator с методом Validate(int age). Метод выбрасывает ArgumentException, если возраст отрицательный или больше 150. Напишите два теста: что для корректного возраста (например, 30) исключение не выбрасывается, и что для некорректного (-5) выбрасывается ArgumentException.

Подсказка

Для проверки исключения используйте Assert.Throws<ArgumentException>(() => ...). Для корректного вызова просто вызовите метод - если он не выбросит исключение, тест пройдёт. Но лучше явно записать результат, чтобы тест что-то проверял.

Решение учителя 
public class AgeValidatorTests{    [Fact]    public void Validate_ValidAge_DoesNotThrow()    {        var validator = new AgeValidator();        var exception = Record.Exception(() => validator.Validate(30));        Assert.Null(exception);    }    [Theory]    [InlineData(-5)]    [InlineData(151)]    [InlineData(200)]    public void Validate_InvalidAge_ThrowsArgumentException(int age)    {        var validator = new AgeValidator();        Assert.Throws<ArgumentException>(() => validator.Validate(age));    }}

Метод Record.Exception из xUnit записывает исключение, если оно было выброшено, или возвращает null, если нет. Это удобный способ проверить, что исключения не было.

Задача 4. Тестирование с моком

Дан интерфейс IEmailSender с методом Send(string to, string message). Есть класс WelcomeService, который при регистрации пользователя вызывает IEmailSender.Send с приветственным сообщением. Напишите тест с моком, который проверяет, что при вызове WelcomeService.Welcome("test@mail.com") метод Send был вызван ровно один раз.

Подсказка

Используйте Moq. Создайте Mock<IEmailSender>, передайте mock.Object в конструктор WelcomeService. После вызова Welcome проверьте: mock.Verify(m => m.Send(It.IsAny<string>(), It.IsAny<string>()), Times.Once).

Решение учителя 
public interface IEmailSender{    void Send(string to, string message);}public class WelcomeService{    private readonly IEmailSender sender;    public WelcomeService(IEmailSender s)    {        sender = s;    }    public void Welcome(string email)    {        sender.Send(email, "Добро пожаловать!");    }}[Fact]public void Welcome_NewUser_SendsEmailOnce(){    // Arrange    var mockSender = new Mock<IEmailSender>();    var service = new WelcomeService(mockSender.Object);    // Act    service.Welcome("test@mail.com");    // Assert    mockSender.Verify(        m => m.Send(It.IsAny<string>(), It.IsAny<string>()),        Times.Once);}

It.IsAny<string>() означает «любая строка». Мы не проверяем конкретное содержимое письма - только факт, что оно было отправлено один раз. Если метод вызовет Send дважды или ни разу - тест упадёт.

Что мы узнали и что дальше

Сегодня мы разобрались с юнит-тестированием - практикой, которая превращает разработку из «надеюсь, работает» в «я знаю, что работает». Узнали, что такое xUnit, как устроена схема Arrange-Act-Assert, как писать параметризованные тесты через [Theory] и как подменять внешние зависимости через моки.

Разобрали:

  • Что такое юнит-тест и зачем он нужен.
  • Схему AAA: Arrange, Act, Assert - три шага любого теста.
  • Атрибуты [Fact] и [Theory] с [InlineData].
  • Основные Assert-методы: Equal, Throws, Null и другие.
  • Проверку граничных случаев - где прячутся самые опасные баги.
  • Моки через Moq - для тестирования кода с зависимостями.

Теперь ваши проекты защищены от регрессий. Вы можете смело рефакторить, добавлять новую функциональность, менять архитектуру - и при этом быть уверенным, что старое не сломалось. Это и есть уровень профессиональной разработки.
