Финальный проект

~60 минут Продвинутый уровень Финал курса

Вот и всё. 31 урок позади: от первого Console.WriteLine до сложных архитектурных решений. Вы прошли путь от «что такое переменная» до создания Telegram-бота. И сегодня - финальная точка. Мы не будем учить новым синтаксическим конструкциям. Вместо этого соберём большое приложение, в котором есть всё, что мы прошли.

Это будет менеджер личных финансов - консольное приложение, которое позволяет добавлять доходы и расходы, сохранять их в файл, строить отчёты и фильтровать операции. Простая идея, но под ней - весь стек: классы, наследование, generics, LINQ, асинхронность, JSON, паттерны и тесты.

Цель урока - не просто «написать ещё одну программу». Цель - показать, как все инструменты соединяются в реальном проекте. Как из маленьких кирпичиков складывается стена. И как из этой стены потом строятся дома.

Архитектура проекта

Прежде чем писать код - подумаем о структуре. Это называется архитектура, и именно она отличает проект, в котором приятно работать, от каши из файлов.

Разделим проект на слои:

  • Модели - сущности данных: Transaction, TransactionType (enum).
  • Хранилище - слой, отвечающий за сохранение и загрузку данных. Интерфейс ITransactionRepository и его реализация JsonTransactionRepository.
  • Сервис - бизнес-логика: FinanceService, который знает, как считать баланс, фильтровать операции, строить отчёты.
  • UI - консольное меню, которое взаимодействует с пользователем и вызывает методы сервиса.

Зачем такое разделение? Затем, что каждый слой можно менять отдельно. Хотите переехать с JSON на SQLite - меняете только ITransactionRepository. Хотите сделать веб-интерфейс вместо консоли - заменяете только UI. Сервис и модели остаются неизменными.

Эта идея называется разделением ответственности (separation of concerns) и лежит в основе большинства современных приложений.

Модели данных

Начнём с самого простого - с того, как мы будем представлять финансовые операции. Тип операции - это либо доход, либо расход. Классический случай для enum:

public enum TransactionType{    Income,    Expense}

Сама операция - это класс с несколькими полями:

public class Transaction{    public Guid Id { get; set; } = Guid.NewGuid();    public DateTime Date { get; set; } = DateTime.Now;    public TransactionType Type { get; set; }    public decimal Amount { get; set; }    public string Category { get; set; } = "";    public string Comment { get; set; } = "";}

Обратите внимание на несколько решений:

  • Guid.NewGuid() - каждую операцию можно удалить по уникальному идентификатору. Это надёжнее, чем индексы в списке, которые меняются при удалении.
  • DateTime.Now - по умолчанию операция датируется сегодняшним числом. Пользователь может поменять дату, если вносит старую операцию.
  • decimal - для денег всегда используем decimal, а не double. Об этом мы говорили ещё в уроке про типы данных.
  • string со значением по умолчанию - чтобы избежать null и связанных с ним проблем.

Хранилище: интерфейс и реализация

Прежде чем писать код сохранения, определим интерфейс. Это как контракт: «любое хранилище, которое я использую, должно уметь загружать и сохранять операции». Конкретная реализация (JSON, база, что угодно) - неважна для остального кода.

public interface ITransactionRepository{    Task<List<Transaction>> LoadAsync();    Task SaveAsync(List<Transaction> transactions);}

Методы асинхронные - потому что в реальности хранилище может быть сетевым или медленным. Сейчас мы работаем с файлом, но интерфейс сразу проектируем так, чтобы завтра можно было перейти на базу данных без изменения остального кода.

Теперь реализация - JSON-хранилище:

using System.Text.Json;public class JsonTransactionRepository : ITransactionRepository{    private readonly string filePath;    public JsonTransactionRepository(string path)    {        filePath = path;    }    public async Task<List<Transaction>> LoadAsync()    {        if (!File.Exists(filePath))            return new List<Transaction>();        string json = await File.ReadAllTextAsync(filePath);        var options = new JsonSerializerOptions        {            PropertyNameCaseInsensitive = true        };        return JsonSerializer.Deserialize<List<Transaction>>(json, options)            ?? new List<Transaction>();    }    public async Task SaveAsync(List<Transaction> transactions)    {        var options = new JsonSerializerOptions { WriteIndented = true };        string json = JsonSerializer.Serialize(transactions, options);        await File.WriteAllTextAsync(filePath, json);    }}

Здесь собрано всё, что мы прошли в трёх уроках подряд: работа с файлами (28), JSON (29), асинхронность (25). Ничего нового - просто комбинация знакомых инструментов.

Сервис: бизнес-логика

Теперь самое интересное - сервис, который знает, что делать с операциями. Он не знает, откуда данные (файл, база, память) - он просто работает с репозиторием.

public class FinanceService{    private readonly ITransactionRepository repo;    private List<Transaction> transactions = new();    public FinanceService(ITransactionRepository repository)    {        repo = repository;    }    public async Task LoadAsync()    {        transactions = await repo.LoadAsync();    }    public async Task AddAsync(Transaction t)    {        transactions.Add(t);        await repo.SaveAsync(transactions);    }    public decimal GetBalance()    {        return transactions.Sum(t =>            t.Type == TransactionType.Income ? t.Amount : -t.Amount);    }    public IEnumerable<Transaction> Filter(        DateTime? from = null,        DateTime? to = null,        TransactionType? type = null)    {        return transactions            .Where(t => !from.HasValue || t.Date >= from)            .Where(t => !to.HasValue || t.Date <= to)            .Where(t => !type.HasValue || t.Type == type)            .OrderByDescending(t => t.Date);    }    public Dictionary<string, decimal> GetCategoryTotals()    {        return transactions            .Where(t => t.Type == TransactionType.Expense)            .GroupBy(t => t.Category)            .ToDictionary(                g => g.Key,                g => g.Sum(t => t.Amount));    }}

Обратите внимание на ключевые моменты:

  • Конструктор принимает интерфейс, а не конкретный класс. Это позволяет в тестах подставить мок, а в продакшене - файл или базу.
  • Метод GetBalance использует LINQ для суммирования: доходы прибавляются, расходы вычитаются. Одной строкой.
  • Метод Filter - отличный пример цепочки Where, где каждый фильтр опционален. Если параметр null - условие пропускается.
  • GetCategoryTotals использует GroupBy и ToDictionary - мощные LINQ-операции, которые превращают список в готовый словарь за пару строк.
Dependency Injection своими руками

То, что FinanceService получает ITransactionRepository в конструкторе - это классический паттерн Dependency Injection (внедрение зависимостей). Сервис не создаёт хранилище сам - он получает готовое. Благодаря этому мы можем подставить в тестах поддельное хранилище, а в реальной программе - настоящее.

Фабрика сервиса

Чтобы не собирать всё вручную в каждом месте, применим паттерн Factory из урока 26. Фабрика создаст готовый FinanceService с нужными зависимостями:

public static class FinanceServiceFactory{    public static FinanceService Create(string dataFilePath)    {        var repo = new JsonTransactionRepository(dataFilePath);        return new FinanceService(repo);    }}

Теперь в Main достаточно вызвать FinanceServiceFactory.Create("data.json") - и всё готово. Если завтра мы решим использовать базу данных вместо JSON - меняется только фабрика, остальной код трогать не нужно.

Консольное меню

Финальный слой - взаимодействие с пользователем. Это самый простой код в проекте: спросить действие, вызвать метод сервиса, показать результат. Вся логика уже спрятана внутри.

static async Task Main(string[] args){    var service = FinanceServiceFactory.Create("data.json");    await service.LoadAsync();    while (true)    {        Console.WriteLine("\n=== Менеджер финансов ===");        Console.WriteLine("1. Добавить доход");        Console.WriteLine("2. Добавить расход");        Console.WriteLine("3. Показать баланс");        Console.WriteLine("4. Показать отчёт по категориям");        Console.WriteLine("5. Показать все операции");        Console.WriteLine("0. Выход");        Console.Write("Выбор: ");        string choice = Console.ReadLine() ?? "";        switch (choice)        {            case "1": await AddTransaction(service, TransactionType.Income); break;            case "2": await AddTransaction(service, TransactionType.Expense); break;            case "3": ShowBalance(service); break;            case "4": ShowCategoryReport(service); break;            case "5": ShowAll(service); break;            case "0": return;            default: Console.WriteLine("Неизвестная команда"); break;        }    }}

Обработчики команд - маленькие методы, каждый из которых делает одну вещь. Это тот самый рефакторинг из урока 27 в действии: не пихать всё в switch, а выносить в отдельные методы с говорящими именами.

static async Task AddTransaction(FinanceService service, TransactionType type){    Console.Write("Сумма: ");    if (!decimal.TryParse(Console.ReadLine(), out decimal amount) || amount <= 0)    {        Console.WriteLine("Некорректная сумма");        return;    }    Console.Write("Категория: ");    string category = Console.ReadLine() ?? "Разное";    var t = new Transaction    {        Type = type,        Amount = amount,        Category = category    };    await service.AddAsync(t);    Console.WriteLine($"Добавлено: {type} {amount:C} ({category})");}

Обратите внимание на decimal.TryParse вместо decimal.Parse. Если пользователь введёт букву - программа не упадёт, а вежливо сообщит об ошибке. Это урок из темы обработки исключений.

Тесты: страховка от регрессий

А теперь - самое важное. Всё, что мы написали, работает. Но как убедиться, что мы не сломаем это завтра? Ответ - юнит-тесты.

Создадим поддельное хранилище для тестов:

public class InMemoryRepository : ITransactionRepository{    private List<Transaction> data = new();    public Task<List<Transaction>> LoadAsync()    {        return Task.FromResult(data.ToList());    }    public Task SaveAsync(List<Transaction> transactions)    {        data = transactions.ToList();        return Task.CompletedTask;    }}

Теперь тест для расчёта баланса:

[Fact]public async Task GetBalance_IncomeAndExpenses_ReturnsCorrectDifference(){    var repo = new InMemoryRepository();    var service = new FinanceService(repo);    await service.LoadAsync();    await service.AddAsync(new Transaction    {        Type = TransactionType.Income,        Amount = 1000,        Category = "Зарплата"    });    await service.AddAsync(new Transaction    {        Type = TransactionType.Expense,        Amount = 300,        Category = "Продукты"    });    decimal balance = service.GetBalance();    Assert.Equal(700, balance);}

Такой тест проверяет главное правило бизнес-логики: доходы прибавляются, расходы вычитаются. Если завтра кто-то случайно перепутает знаки - тест сразу упадёт. И это спасёт от серьёзного бага.

Подобные тесты можно написать для фильтрации, группировки по категориям, обработки пустого списка. Именно так выглядит работа профессионального разработчика: код пишется один раз, тестами проверяется сотни раз.

Если что-то не работает

Финальный блок - про типичные проблемы, с которыми сталкиваются на реальных проектах.

  • «Программа работает, но данные теряются». Скорее всего, метод AddAsync добавил транзакцию в память, но не вызвал SaveAsync. Всегда сохраняйте после изменений, либо используйте подход, где AddAsync сам вызывает сохранение (как в нашем примере).
  • «Не могу найти файл data.json». Он создаётся в рабочей директории программы, а не там, где вы его ищете. Используйте Directory.GetCurrentDirectory() или передавайте полный путь явно.
  • «JSON не читается обратно». Часто проблема в кодировке или в несовпадении имён полей. Проверьте PropertyNameCaseInsensitive = true при десериализации. И убедитесь, что классы, которые сохраняли, и те, которые читают - это одни и те же классы с одинаковыми свойствами.
  • «Тесты падают, но программа работает». Возможно, в тестах поддельное хранилище, а в программе - настоящее, и они ведут себя по-разному. Проверьте, что InMemoryRepository действительно возвращает то, что сохранил.
  • «Код работает, но его стыдно показывать». Значит, пора применить рефакторинг. Разделите длинные методы, вынесите магические числа в константы, дайте переменным понятные имена. Вспомните урок 27 - там всё подробно.
  • «Я не понимаю, с чего начать свой проект». Начните с модели данных. Определите, какие сущности есть в вашей предметной области. Потом интерфейсы для их хранения. Потом сервис с бизнес-логикой. UI - в самом конце. Именно такой порядок используется в реальной разработке.
  • «Хочу дальше, но не знаю, куда двигаться». Практика. Возьмите знакомый проект и перепишите его заново - с архитектурой, тестами, обработкой ошибок. Возьмите чужой open-source проект с GitHub и разберитесь, как он устроен. Участвуйте в pet-проектах с друзьями. Опыт приходит только через практику.

Практика

Задача 1. Удаление операции

Добавьте в FinanceService метод RemoveAsync(Guid id), который удаляет операцию по её идентификатору и сохраняет изменения. Добавьте в меню пункт «Удалить операцию».

Подсказка

Используйте List.RemoveAll с лямбдой: transactions.RemoveAll(t => t.Id == id). После этого вызовите repo.SaveAsync(transactions). В меню попросите у пользователя ID и преобразуйте через Guid.TryParse.

Решение учителя 
public async Task<bool> RemoveAsync(Guid id){    int removed = transactions.RemoveAll(t => t.Id == id);    if (removed > 0)    {        await repo.SaveAsync(transactions);        return true;    }    return false;}

Метод возвращает bool - чтобы UI мог сообщить, было ли что-то удалено. Если операция с таким ID не найдена - RemoveAll вернёт 0, и мы не будем зря сохранять файл.

Задача 2. Отчёт по месяцам

Добавьте в сервис метод GetMonthlyReport(), который возвращает словарь «месяц-год → сумма расходов за месяц». Например: "2025-03" → 15000. Используйте LINQ для группировки по месяцу.

Подсказка

Сначала отфильтруйте расходы через Where(t => t.Type == TransactionType.Expense). Потом сгруппируйте через GroupBy(t => t.Date.ToString("yyyy-MM")) - формат yyyy-MM превратит дату в строку «год-месяц». И наконец ToDictionary с суммой по каждой группе.

Решение учителя 
public Dictionary<string, decimal> GetMonthlyReport(){    return transactions        .Where(t => t.Type == TransactionType.Expense)        .GroupBy(t => t.Date.ToString("yyyy-MM"))        .OrderBy(g => g.Key)        .ToDictionary(            g => g.Key,            g => g.Sum(t => t.Amount));}

Цепочка из четырёх LINQ-методов решает задачу, на которую с циклами ушло бы 15-20 строк. Именно за это мы и любим LINQ.

Задача 3. Экспорт в CSV

Добавьте в меню пункт «Экспорт в CSV», который сохраняет все операции в файл export.csv в формате: Дата;Тип;Сумма;Категория;Комментарий. Каждая операция - отдельная строка. В конце выведите сообщение с путём к файлу и количеством записанных строк.

Подсказка

Используйте StringBuilder (урок 20) для эффективной сборки строк. Или LINQ Select + string.Join. Разделитель - точка с запятой, потому что запятая может встречаться в комментариях. Формат даты - yyyy-MM-dd HH:mm.

Решение учителя 
public async Task ExportToCsvAsync(string path){    var sb = new StringBuilder();    sb.AppendLine("Дата;Тип;Сумма;Категория;Комментарий");    foreach (var t in transactions.OrderByDescending(t => t.Date))    {        sb.AppendLine($"{t.Date:yyyy-MM-dd HH:mm};{t.Type};" +                      $"{t.Amount};{t.Category};{t.Comment}");    }    await File.WriteAllTextAsync(path, sb.ToString());}

CSV с разделителем-точкой с запятой откроется в Excel без танцев с настройками. Такой формат удобен для бухгалтерских задач и импорта в другие системы.

У каждого свой список, но вот что часто называют выпускники:

  • Код пишется для людей. Понятные имена, короткие методы, отсутствие магических чисел - теперь это привычка, а не повод для раздражения.
  • Ошибки - это нормально. Исключения вместо падений, тесты вместо «надеюсь, работает», отладка вместо «перепишу заново».
  • Думаю об архитектуре. Разделение на слои, интерфейсы, внедрение зависимостей - это уже не «для больших проектов», а база.
  • Async - это просто. Раньше казалось магией, теперь - осознанный инструмент для операций ввода-вывода.
  • LINQ экономит часы. Вместо десяти циклов - одна цепочка методов, которую можно прочитать вслух.
  • Тесты спасают. Один раз почувствовав, как тест поймал баг в новой функции, уже не хочется работать без них.
  • Паттерны - это язык. Говорить «здесь нужен Strategy» и быть понятым - бесценно при работе в команде.

Главное - не просто «знать», а применять. Курс дал вам инструменты. Дальше - только практика, проекты и постоянное обучение. Именно так программисты растут: от junior к middle, от middle к senior.

Курс завершён

Вот и всё. 32 урока позади. Если в начале курса вы не знали, что такое переменная, а сейчас можете написать приложение с архитектурой, тестами и асинхронностью - это огромный прогресс. Большинство людей, которые говорят «хочу выучить C#», до этого уровня не доходят.

Давайте оглянемся на пройденный путь:

  • Начальный уровень (12 уроков) - от первой программы до массивов и коллекций. База синтаксиса, без которой дальше не двинуться.
  • Средний уровень (10 уроков) - методы, классы, ООП, исключения. От «написать скрипт» до «собрать проект».
  • Продвинутый уровень (10 уроков) - generics, LINQ, асинхронность, паттерны, тесты. От «работает» до «работает правильно и надёжно».

Вместе это полный набор знаний junior C#-разработчика. Всё, что нужно, чтобы уверенно проходить собеседования, брать первые заказы или развиваться в выбранном направлении.

Что делать дальше

Программирование - это не «выучил и забыл». Это навык, который живёт только через постоянную практику. Несколько конкретных шагов:

  • Сделайте свой проект. Не учебный, а свой - для себя, для друзей, для работы. Тема неважна. Важен процесс: от идеи до рабочей программы.
  • Читайте чужой код. Возьмите популярный open-source проект на GitHub и разберитесь, как он устроен. Это лучший способ увидеть, как думают опытные разработчики.
  • Не бойтесь сложного. Первый раз всегда страшно. Но через неделю упорной работы даже ASP.NET или Entity Framework перестанут казаться магией.
  • Следите за экосистемой. C# развивается каждый год: новые версии языка, новые возможности .NET. Читайте блоги Microsoft, смотрите конференции (dotnetConf, .NET Conf), подписывайтесь на сообщества.
  • Помогайте другим. Объясняя что-то новичкам, вы сами начинаете понимать глубже. Это работает безотказно.

И помните главное: программирование - это не про знание синтаксиса, а про умение решать задачи. Синтаксис приходит с опытом, а решение задач - это навык, который тренируется только практикой. Пишите код, ломайте, чините, рефакторьте. Именно так растут разработчики.

Спасибо, что были с нами все 32 урока. Удачи в дальнейшем пути. И пусть ваш код компилируется с первого раза.
