Рефакторинг

~45 минут Продвинутый уровень Теория и Практика

В прошлом уроке мы разобрали паттерны проектирования. Сегодня поговорим о навыке, который отличает хорошего разработчика от отличного - об умении улучшать код. Программа может работать без ошибок, но при этом быть нечитаемой, запутанной и сложной в поддержке. Процесс улучшения внутренней структуры кода без изменения его внешнего поведения называется рефакторингом.

Представьте, что вы переехали в новую квартиру. Вещи распакованы, мебель стоит, жить можно. Но провода от компьютера тянутся через всю комнату, вещи в шкафу лежат вперемешку, а на кухне ничего не найти. Рефакторинг - это генеральная уборка и перестановка. Квартира та же, функции те же, но жить в ней становится в разы приятнее.

Зачем нужен рефакторинг

Код пишется один раз, а читается и изменяется сотни раз. Если через полгода вам нужно будет добавить новую функцию, плохо написанный код превратит эту задачу в кошмар. Рефакторинг решает несколько проблем:

  • Читаемость. Понятные имена переменных и короткие методы экономят часы разработки.
  • Поддерживаемость. В коде без дублирования легче найти ошибку и исправить её в одном месте, а не в пяти.
  • Масштабируемость. Хорошо структурированный код проще расширять новыми функциями.
  • Снижение технического долга. Чем дольше вы откладываете рефакторинг, тем дороже он становится.
Золотое правило

Рефакторинг не меняет поведение программы. Если после ваших изменений пользователь увидел новые кнопки или изменилась логика работы - это не рефакторинг, а переписывание. Для проверки неизменности поведения идеально подходят автоматические тесты, но о них мы поговорим в уроке 30.

Признаки плохого кода

Прежде чем что-то улучшать, нужно научиться замечать проблемы. Вот самые частые «запахи кода» (code smells), которые сигналят о необходимости рефакторинга.

1. Магические числа

Это числа, смысл которых непонятен без контекста. Например:

if (user.Age > 18){    discount = price * 0.85;}

Что такое 0.85? Скидка 15%? Коэффициент налога? Через месяц вы сами забудете, откуда взялось это число. Решение - вынести в константу с понятным именем:

const decimal ADULT_DISCOUNT = 0.85m;if (user.Age > 18){    discount = price * ADULT_DISCOUNT;}

2. Дублирование кода (копипаста)

Главный враг программиста. Если вы скопировали кусок кода и вставили его в другое место - при следующем изменении логики вам придётся править его в двух местах. И обязательно где-то забудете.

Решение - вынести повторяющуюся логику в отдельный метод.

3. Длинные методы

Метод, который занимает 100 строк, делает слишком много. Его сложно читать и тестировать. Хороший метод должен решать одну задачу и обычно занимать не больше 10-20 строк. Если больше - разбивайте на подметоды.

4. Плохие имена

Переменные a, b, data1, temp или методы DoIt(), Process() не несут никакой информации. Имена должны отвечать на вопрос «что здесь лежит» или «что делает этот метод». userAge лучше, чем x. CalculateTotalPrice() лучше, чем DoMath().

5. Глубокие вложенности

Когда внутри if находится ещё один if, а в нём - третий, читать код становится очень сложно. Часто вложенность можно убрать с помощью раннего возврата (guard clauses).

Пример: рефакторинг «до и после»

Давайте посмотрим на реальный пример плохого кода и постепенно его улучшим.

Исходный код (плохо)

public void ProcessOrder(Order order){    if (order != null)    {        if (order.Items.Count > 0)        {            decimal total = 0;            foreach (var item in order.Items)            {                total += item.Price * item.Quantity;            }            if (order.Customer.IsVip)            {                total = total * 0.9m;            }            Console.WriteLine($"Итог: {total}");        }        else        {            Console.WriteLine("Пустой заказ");        }    }}

Что здесь не так? Глубокая вложенность, магическое число 0.9, смешение разных задач в одном методе (проверка, расчёт, вывод).

Шаг 1: ранний возврат

Избавимся от вложенности, проверяя плохие условия в начале и сразу выходя из метода.

public void ProcessOrder(Order order){    if (order == null) return;    if (order.Items.Count == 0)    {        Console.WriteLine("Пустой заказ");        return;    }    decimal total = 0;    foreach (var item in order.Items)    {        total += item.Price * item.Quantity;    }    if (order.Customer.IsVip)    {        total = total * 0.9m;    }    Console.WriteLine($"Итог: {total}");}

Уже легче читать: сначала отсекаем плохие сценарии, потом идёт основная логика.

Шаг 2: вынос константы и расчёта в отдельный метод

Уберём магическое число и разделим ответственность. Метод CalculateTotal будет только считать сумму, а ProcessOrder - управлять процессом.

private const decimal VIP_DISCOUNT = 0.9m;public void ProcessOrder(Order order){    if (order == null) return;    if (order.Items.Count == 0)    {        Console.WriteLine("Пустой заказ");        return;    }    decimal total = CalculateTotal(order);    Console.WriteLine($"Итог: {total}");}private decimal CalculateTotal(Order order){    decimal sum = 0;    foreach (var item in order.Items)    {        sum += item.Price * item.Quantity;    }    return order.Customer.IsVip ? sum * VIP_DISCOUNT : sum;}

Теперь код читается как книга: «Если заказ пустой - выведи сообщение и выйди. Иначе посчитай итог и выведи его». Логика расчёта спрятана в отдельном методе, который легко протестировать.

Когда заниматься рефакторингом

Есть популярное правило: правило скаута. Оно звучит так: «Оставляй место стоянки чище, чем оно было до тебя». В программировании это значит: если вы зашли в файл, чтобы добавить функцию или исправить баг - заодно поправьте то, что явно бросается в глаза.

Однако не стоит устраивать рефакторинг ради рефакторинга. Если код работает и понятен - не трогайте его. Особенно опасен масштабный рефакторинг перед дедлайном, когда нужно выпустить новую функцию. Лучший подход - маленькие постоянные улучшения.

Шпаргалка

Самое важное в одном месте:

  • Рефакторинг улучшение кода без изменения поведения
  • DRY не повторяйся
  • Guard clauses ранние возвраты вместо вложенности
  • Магические числа заменить на константы
  • Короткие методы одна задача - один метод
  • Понятные имена переменные и методы говорят сами за себя
  • Правило скаута оставляй код чище, чем он был

Если что-то не работает

Разберём типичные заблуждения и проблемы, связанные с рефакторингом.

  • «Если код работает - не трогай его». Это правда, если код действительно понятен и прост. Но если вы с трудом понимаете свой же код недельной давности - рефакторинг необходим. Иначе через месяц вы потратите на новую функцию в три раза больше времени.
  • «Рефакторинг и оптимизация - это одно и то же». Нет. Оптимизация делает программу быстрее. Рефакторинг делает код чище. Часто после рефакторинга программа даже замедляется (например, если разбить один большой цикл на несколько маленьких методов). Это нормально: сначала чистый код, потом - при необходимости - оптимизация.
  • «Я перепишу всё с нуля, так быстрее». Полное переписывание - очень рискованно. Вы можете упустить неочевидные детали, забыть про граничные случаи, которые обрабатывал старый код. Постепенный рефакторинг безопаснее и почти всегда быстрее.
  • «Рефакторинг нужен только для старых проектов». Нет. Рефакторинг - это привычка, которую нужно применять постоянно, пока код свежий. Если запустить проект и не следить за качеством кода - через полгода он превратится в тот самый «старый проект».
  • «Имена переменных неважны, главное - чтобы работало». Имена - это документация, которая всегда с вами. Хорошее имя totalPrice избавляет от необходимости писать комментарий «здесь лежит общая стоимость». Плохое имя t заставляет каждого читателя кода напрягать мозг.
  • «Комментарии заменяют плохие имена». Комментарии - это «запах кода». Хороший код понятен без комментариев. Если вам нужно объяснить, что делает переменная или метод - проще переименовать их, чем писать комментарий. А те комментарии, которые всё же нужны, должны объяснять почему сделано именно так, а не что делает код.

Если что-то не получается - напишите нам в Telegram, разберёмся вместе.

Практика

Четыре задачи по возрастающей сложности. У каждой есть подсказка и решение учителя.

Задача 1. Магические числа

Перед вами метод, который проверяет, может ли пользователь получить кредит. В нём есть несколько магических чисел. Замените их на понятные константы.

public bool CanGetCredit(User user, decimal amount){    if (user.Age < 21) return false;    if (user.Age > 65) return false;    if (amount > 5000000) return false;    return true;}
Подсказка

Числа 21, 65 и 5000000 несут конкретный бизнес-смысл. Вынесите каждое в отдельную const или static readonly переменную с говорящим именем. Например, MIN_CREDIT_AGE, MAX_CREDIT_AGE, MAX_CREDIT_AMOUNT.

Решение учителя 
private const int MIN_CREDIT_AGE = 21;private const int MAX_CREDIT_AGE = 65;private const decimal MAX_CREDIT_AMOUNT = 5_000_000m;public bool CanGetCredit(User user, decimal amount){    if (user.Age < MIN_CREDIT_AGE) return false;    if (user.Age > MAX_CREDIT_AGE) return false;    if (amount > MAX_CREDIT_AMOUNT) return false;    return true;}
Задача 2. Убираем дублирование

В коде есть два метода, которые выводят приветствие для разных ролей. Найдите в них дублирующийся код и вынесите его в отдельный метод.

public void GreetAdmin(string name){    Console.WriteLine("=================");    Console.WriteLine($"Добро пожаловать, {name}!");    Console.WriteLine("Вы вошли как администратор");    Console.WriteLine("=================");}public void GreetUser(string name){    Console.WriteLine("=================");    Console.WriteLine($"Добро пожаловать, {name}!");    Console.WriteLine("Вы вошли как пользователь");    Console.WriteLine("=================");}
Подсказка

Обратите внимание: единственное отличие - это строка с ролью. Всё остальное (рамка и приветствие) повторяется. Создайте метод PrintGreeting(string name, string role) и вызывайте его из обоих мест.

Решение учителя 
public void GreetAdmin(string name){    PrintGreeting(name, "администратор");}public void GreetUser(string name){    PrintGreeting(name, "пользователь");}private void PrintGreeting(string name, string role){    Console.WriteLine("=================");    Console.WriteLine($"Добро пожаловать, {name}!");    Console.WriteLine($"Вы вошли как {role}");    Console.WriteLine("=================");}
Задача 3. Ранний возврат

Метод ниже проверяет данные пользователя перед сохранением. Упростите его с помощью ранних возвратов (guard clauses), убрав вложенность.

public bool ValidateUser(User user){    if (user != null)    {        if (!string.IsNullOrEmpty(user.Name))        {            if (user.Age >= 18)            {                if (user.Email.Contains("@"))                {                    return true;                }            }        }    }    return false;}
Подсказка

Вместо того чтобы проверять хорошие условия и вкладывать их друг в друга, проверяйте плохие. Если что-то не так - сразу return false. В конце метода - return true, потому что все проверки пройдены.

Решение учителя 
public bool ValidateUser(User user){    if (user == null) return false;    if (string.IsNullOrEmpty(user.Name)) return false;    if (user.Age < 18) return false;    if (!user.Email.Contains("@")) return false;    return true;}

Код стал линейным, плоским и читается сверху вниз, как список требований к пользователю.

Задача 4. Большой рефакторинг

Перед вами метод, который обрабатывает заказ. В нём смешаны проверка, расчёт скидки, расчёт налога и вывод на экран. Разбейте его на несколько маленьких методов с говорящими именами.

public void HandleOrder(Order order){    if (order == null) return;    decimal subtotal = 0;    foreach (var item in order.Items)    {        subtotal += item.Price * item.Quantity;    }    decimal discount = 0;    if (subtotal > 10000)    {        discount = subtotal * 0.1m;    }    decimal tax = (subtotal - discount) * 0.2m;    decimal total = subtotal - discount + tax;    Console.WriteLine($"Подытог: {subtotal}");    Console.WriteLine($"Скидка: {discount}");    Console.WriteLine($"Налог: {tax}");    Console.WriteLine($"Итого: {total}");}
Подсказка

Разделите ответственность. Один метод - расчёт подытога. Второй - расчёт скидки. Третий - расчёт налога. Четвёртый - вывод результатов. Пятый (HandleOrder) - оркестратор, который вызывает остальные в правильном порядке.

Решение учителя 
public void HandleOrder(Order order){    if (order == null) return;    decimal subtotal = CalculateSubtotal(order);    decimal discount = CalculateDiscount(subtotal);    decimal tax = CalculateTax(subtotal - discount);    decimal total = subtotal - discount + tax;    PrintReceipt(subtotal, discount, tax, total);}private decimal CalculateSubtotal(Order order){    decimal sum = 0;    foreach (var item in order.Items)    {        sum += item.Price * item.Quantity;    }    return sum;}private decimal CalculateDiscount(decimal subtotal){    return subtotal > 10000 ? subtotal * 0.1m : 0;}private decimal CalculateTax(decimal amount){    return amount * 0.2m;}private void PrintReceipt(decimal subtotal, decimal discount, decimal tax, decimal total){    Console.WriteLine($"Подытог: {subtotal}");    Console.WriteLine($"Скидка: {discount}");    Console.WriteLine($"Налог: {tax}");    Console.WriteLine($"Итого: {total}");}

Теперь каждый метод делает одну вещь. Если изменится формула расчёта скидки - вы откроете CalculateDiscount и поменяете только её. Остальной код не тронете.

Что мы узнали и что дальше

Сегодня мы разобрались с рефакторингом - навыком, который делает код не просто рабочим, а удобным для жизни. Узнали, что такое «запахи кода»: магические числа, дублирование, длинные методы, плохие имена и глубокая вложенность. И самое главное - научились с ними бороться.

На примерах разобрали, как выносить константы, убирать дублирование через новые методы, использовать ранние возвраты для упрощения условий и разбивать большие методы на маленькие, каждый из которых решает одну задачу.

Запомните главное правило: рефакторинг не меняет поведение программы. Если после ваших изменений пользователь заметил что-то новое - это уже не рефакторинг. Поэтому так важно делать маленькие шаги и проверять, что всё работает.
